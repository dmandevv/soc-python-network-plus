# 1.8 — Summarize evolving use cases for modern network environments

## SDN and SD-WAN

### Software-defined network (SDN)
Separates the **control plane** (deciding where traffic goes) from the **data plane** (actually forwarding it), moving control decisions to a **centralized controller** rather than leaving each device to decide independently.

**Traditional networking:** every switch and router runs its own control plane — its own routing protocol instance, its own view, its own decisions. Configuration is per-device, and consistency depends on doing the same thing correctly on fifty boxes.

**SDN:** the controller holds a network-wide view and programs the forwarding tables of devices beneath it. Devices become forwarding hardware; intelligence lives centrally.

**What that enables:**
- **Central policy management** — define intent once, applied everywhere
- **Programmability** — the network is configured through APIs, so it can be automated and version-controlled
- **Network-wide optimization** — decisions made with full topology visibility rather than each device's local view

**Its tradeoff:** the controller becomes a critical dependency and a high-value target. Controller redundancy is essential, and compromising it means compromising the network's entire forwarding behaviour.

**SDN vs. NFV:** SDN moves the **control plane** off devices ("who decides?"). NFV moves **network functions** off dedicated hardware ("what runs it?"). Complementary, frequently deployed together, and commonly confused.

### Software-defined WAN (SD-WAN)
SDN principles applied to the **wide area network** — centralized control over how branch offices connect, layered on top of whatever transport is available.

**The problem it solves:** traditional WANs used expensive MPLS circuits in a hub-and-spoke design, forcing all traffic through headquarters. With SaaS and cloud services, that means a branch reaching Microsoft 365 backhauls to HQ, out to the internet, and back — high latency for no benefit, on the most expensive link the organization buys.

**Its four defining traits:**

| Trait | Meaning |
|---|---|
| **Transport agnostic** | Uses MPLS, broadband, LTE, or satellite interchangeably; can bond several together |
| **Application aware** | Identifies traffic by application, not just port, and steers it accordingly |
| **Zero-touch provisioning** | A new device ships to a branch, is plugged in, and pulls its configuration automatically |
| **Central policy management** | Intent defined once, applied across all sites |

**The result:** cheap broadband carries what tolerates it, MPLS carries what needs guarantees, SaaS traffic goes direct to the internet instead of tromboning through HQ, and branch-to-branch traffic takes direct tunnels.

**SDN vs. SD-WAN:** SD-WAN is SDN's architecture (central control, programmability) **plus** WAN-specific capabilities. The two traits it does *not* share with general SDN are **application awareness** and **transport agnosticism** — both only meaningful across a WAN.

## VXLAN

### Virtual Extensible LAN (VXLAN)
An overlay that **encapsulates Layer 2 Ethernet frames inside Layer 3 UDP packets** (MAC-in-UDP), letting a Layer 2 segment span a routed network.

**The two problems it solves:**

**Scale.** A VLAN ID is **12 bits** → 4,094 usable segments. A VXLAN Network Identifier (**VNI**) is **24 bits** → about **16 million**. In a cloud provider serving thousands of tenants, 4,094 is exhausted almost immediately.

**Reach.** A VLAN is confined to a Layer 2 domain. VXLAN wraps frames in IP, so a segment can stretch across a routed fabric or between data centres — which is what allows a VM to migrate between sites while keeping its address.

**How it works:** endpoints called **VTEPs** (VXLAN Tunnel Endpoints) perform the encapsulation. A frame leaving a host is wrapped by the local VTEP with a VXLAN header carrying the VNI, then a UDP/IP header addressed to the remote VTEP. The underlying network only ever sees ordinary routed IP traffic.

**Why this pairs with spine-and-leaf:** the fabric underlay is routed (so ECMP uses every link and STP is absent), while VXLAN provides the Layer 2 adjacency that applications still expect. Leaf switches act as the VTEPs.

**Cost:** the encapsulation adds roughly 50 bytes of overhead, so underlay MTU must be raised — commonly to 9000-byte jumbo frames — or traffic fragments.

### Data center interconnect (DCI)
The umbrella term for the technologies linking **multiple data centres into one logical network**. VXLAN is a common way to implement it, which is why the objectives list DCI beneath VXLAN.

**Why organizations need it:**
- **Disaster recovery** — replicating workloads and data to a second site
- **Workload mobility** — migrating VMs between sites, ideally without renumbering
- **Active-active operation** — both sites serving traffic simultaneously
- **Capacity** — spilling into a second facility when the first fills

**What makes it hard:** applications frequently assume **Layer 2 adjacency** — same subnet, same broadcast domain — but data centres are separated by routed WAN links. Stretching Layer 2 across them is what DCI technologies provide, and VXLAN is the modern method.

**The risk of stretched Layer 2:** a broadcast storm or a Layer 2 loop in one data centre can propagate to the other, turning two independent failure domains into one. That is the argument against extending Layer 2 further than necessary — and why designs increasingly prefer routing between sites with Layer 2 stretched only where an application genuinely demands it.

### Layer 2 encapsulation
The mechanism underpinning both terms above: **wrapping a complete Ethernet frame inside a Layer 3 packet** so it can traverse routed infrastructure that would otherwise drop it.

VXLAN is the dominant implementation; older equivalents include OTV and L2TPv3, and **GRE** does the same thing for Layer 3 payloads. The common idea is that encapsulation lets a network carry traffic its own topology could not natively support.

## Zero trust architecture (ZTA)

A security model that **removes implicit trust based on network location**. Nothing is trusted because of where it sits — every request is authenticated and authorized regardless of whether it originates inside or outside the network.

**The model it replaces** is perimeter security: a hardened boundary with a trusted interior. That fails for reasons the earlier material already established — **east-west traffic never crosses the perimeter**, so an attacker inside moves laterally through traffic no firewall inspects. Cloud services, remote work, and BYOD also erased the boundary itself: there is no longer a clean "inside."

**Its guiding assumption: assume breach.** Design as though an attacker is already on the network, because eventually they will be.

**The three principles CompTIA lists:**

| Principle | Meaning |
|---|---|
| **Policy-based authentication** | Identity verified per request against policy, not once at a boundary |
| **Authorization** | Verified identity still only grants what policy explicitly permits |
| **Least privilege access** | Each identity receives the minimum access needed, nothing more |

**How it appears in practice:** microsegmentation between internal systems, MFA everywhere, device posture checks, continuous verification rather than one-time login, and **ZTNA** replacing VPNs — granting access to specific applications rather than placing a device on the network.

## SASE and SSE

### Secure Access Service Edge (SASE)
A framework converging **networking and security into a single cloud-delivered service**, with policy enforced at a distributed edge close to users rather than at a corporate data centre.

**The problem it addresses:** the traditional model backhauled all traffic to headquarters so it could pass the security stack there. With users remote and applications in the cloud, that means a laptop reaching a SaaS application routes through an office it never needs to touch — adding latency to protect a perimeter that no longer contains anything.

**SASE moves the security stack to the cloud edge.** Users connect to the nearest point of presence, policy is enforced there, and traffic proceeds directly to its destination.

**Its components:**

| Networking | Security (= SSE) |
|---|---|
| **SD-WAN** | **SWG** — secure web gateway |
| | **CASB** — cloud access security broker |
| | **ZTNA** — zero trust network access |
| | **FWaaS** — firewall as a service |

### Security Service Edge (SSE)
**SASE without the networking half** — the cloud-delivered security stack alone (SWG, CASB, ZTNA, FWaaS), with no SD-WAN component.

**Why it exists as a separate term:** many organizations want cloud-delivered security without replacing their existing WAN. SSE lets them adopt the security half independently.

> **SASE = SD-WAN + SSE.** SSE is the security-only subset.

## Infrastructure as code (IaC)

Defining and provisioning infrastructure through **machine-readable definition files** rather than manual configuration. The desired state is written down, version-controlled, and applied by tooling.

**What it replaces:** logging into devices and configuring them by hand — a process that is slow, inconsistent between engineers, undocumented after the fact, and impossible to reproduce reliably.

**What it provides:**
- **Repeatability** — the same definition produces the same result every time
- **Version control** — infrastructure changes reviewed, diffed, and rolled back like code
- **Documentation by construction** — the files *are* the record of what exists
- **Speed and scale** — provisioning fifty devices costs the same effort as one
- **Disaster recovery** — rebuild from definitions rather than from memory

**Why it applies to networking at all:** it depends on devices being programmable through APIs, which is what SDN's centralized, API-driven control made possible. Tools include Terraform, Ansible, Puppet, and Chef.

**A concept worth knowing: idempotency.** Applying the same definition repeatedly produces the same end state rather than compounding changes — running it twice is safe, which is what makes automated reconciliation possible.

### Automation

The execution half of IaC — tooling that applies definitions to real devices. CompTIA lists four elements:

**Playbooks / templates / reusable tasks**
A **playbook** is an ordered set of tasks describing what to configure (Ansible's term). A **template** is a parameterised configuration — one VLAN definition with variables filled in per site, rather than fifty near-identical files. **Reusable tasks** are common operations written once and called wherever needed. Together they mean a change is made in one place and applied everywhere.

**Configuration drift / compliance**
**Drift** is the gap that opens between the defined state and reality — someone makes an emergency change at 2 a.m. and never records it, and the device no longer matches its definition. Automation detects drift by comparing actual configuration against the source of truth, and **compliance** enforcement either alerts on the difference or corrects it automatically. This is why idempotency matters: reconciliation can run continuously without side effects.

**Upgrades**
Firmware and OS updates rolled out through automation rather than device by device — consistent versions, staged rollouts, and a defined rollback. Manual upgrades across a fleet are where version sprawl comes from.

**Dynamic inventories**
An inventory is the list of devices automation acts on. A **static** inventory is a hand-maintained file that goes stale. A **dynamic inventory** queries an authoritative source at runtime — a cloud API, IPAM, or CMDB — so newly provisioned devices are managed automatically and decommissioned ones drop out. Essential in elastic environments where the device list changes constantly.

> **Note the official term is "dynamic inventories."** Some third-party practice material uses "dynamic repositories," which is not CompTIA's wording.

### Source control

Managing the definition files themselves — the discipline that makes IaC trustworthy rather than just scripted. CompTIA lists four elements:

**Version control**
The system tracking every change over time — who changed what, when, and why. Git is the standard. Its value is **history and reversibility**: a bad change is identified and rolled back to a known-good state, rather than reconstructed from memory.

**Central repository**
The **single authoritative location** all definitions live in and every tool pulls from. Without it, engineers work from divergent local copies and there is no answer to "what is the current configuration?" The repository *is* the source of truth that drift is measured against.

**Conflict identification**
When two people modify the same file simultaneously, version control **detects the collision and refuses to silently overwrite**, requiring a human to reconcile the changes. Without this, the second save destroys the first with no indication anything was lost.

**Branching**
Working on a copy isolated from the main line, then merging when ready. This allows a change to be developed and tested without affecting the production definition, and supports review before merging — the network equivalent of change control, enforced by tooling.

> **Version control is the *mechanism*; central repository is the *location*.** Exam questions distinguishing them hinge on that: "single point of reference for all configurations" is the **central repository**.

## IPv6 addressing

### Mitigating address exhaustion
IPv6 uses **128-bit** addresses against IPv4's 32-bit, giving roughly **3.4 × 10³⁸** addresses — enough that every device can hold a globally unique one with no scarcity.

**What that removes:** NAT becomes unnecessary. Every host can be globally addressable, restoring the **end-to-end connectivity** IPv4 lost — which simplifies peer-to-peer applications, VoIP, and anything that struggles behind NAT.

**Other improvements:** a simplified fixed-length header for faster router processing, no broadcast at all (multicast replaces it), **SLAAC** for address autoconfiguration without a DHCP server, and mandatory support for IPsec.

**Address format:** eight groups of four hex digits separated by colons, with two shortening rules — leading zeros in a group may be dropped, and **one** run of consecutive all-zero groups may be replaced by `::`. Only one `::` per address, or the expansion would be ambiguous.

```
2001:0db8:0000:0000:0000:ff00:0042:8329
2001:db8::ff00:42:8329          ← same address
```

**Key ranges:** `2000::/3` global unicast (routable), **`fe80::/10` link-local** (self-assigned, every interface has one), `fc00::/7` unique local (the private-address equivalent), `ff00::/8` multicast, `::1/128` loopback.

**Why adoption is slow despite the benefits:** IPv4 with NAT works well enough, dual-stack means running two protocols, and older equipment lacks support. The transition mechanisms below exist because both protocols will coexist for years.

### Compatibility — Tunneling
**Encapsulating IPv6 packets inside IPv4 headers** so IPv6 traffic can cross IPv4-only infrastructure. The intervening network sees ordinary IPv4 and needs no IPv6 support.

**Where it applies:** two IPv6 islands separated by an IPv4-only path — a site whose ISP does not offer IPv6, or an internal network that supports it while the WAN does not.

**Named implementations:** **6to4** (`2002::/16`), **Teredo** (`2001::/32`, works from behind NAT), **6in4**, and **ISATAP**.

**Its cost:** encapsulation overhead reduces effective MTU, and tunnel endpoints add latency and a potential bottleneck. It is a transitional workaround, not a destination.

### Compatibility — Dual stack
Running **IPv4 and IPv6 simultaneously** on the same devices and interfaces, each with its own address and routing table. **No encapsulation and no translation** — both protocols operate natively and independently, and applications use whichever the destination supports.

**Why it is the preferred approach:** nothing is wrapped or rewritten, so there is no overhead, no MTU reduction, and no translation breaking protocols that embed addresses in their payloads.

**Its cost is operational:** two protocols to configure, secure, monitor, and troubleshoot. **Firewall rules must be written twice** — an IPv4 rule does not filter IPv6 traffic. That gap is a genuine and frequent security oversight: a host hardened on IPv4 while its IPv6 stack sits wide open.

### Compatibility — NAT64
**Translating** between IPv6 and IPv4 — rewriting packets rather than encapsulating them — so an **IPv6-only** client can reach an **IPv4-only** server.

**How it differs from tunneling:** tunneling wraps IPv6 inside IPv4 with both endpoints speaking IPv6. NAT64 converts one protocol into the other, and the endpoints never share a protocol at all.

**Usually paired with DNS64**, which synthesises an IPv6 address for an IPv4-only destination so the client has something to connect to.

**Where it is used:** IPv6-only networks — notably mobile carriers — that still need reachability to the IPv4 internet. It carries NAT's usual problems, breaking protocols that embed IP addresses in their payloads.

| Mechanism | Method | Endpoints |
|---|---|---|
| **Tunneling** | **Encapsulate** IPv6 in IPv4 | Both IPv6 |
| **Dual stack** | **Neither** — run both natively | Both, independently |
| **NAT64** | **Translate** between protocols | IPv6 client, IPv4 server |
