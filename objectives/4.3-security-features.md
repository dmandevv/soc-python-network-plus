# 4.3 — Given a scenario, apply network security features, defense techniques, and solutions

Where [4.1](4.1-security-concepts.md) is vocabulary and [4.2](4.2-attacks.md) is what goes wrong, **4.3 is the countermeasures** — and the exam phrases it as *"given a scenario,"* meaning questions describe a situation and ask which control fits.

**Official term list:**

- Device hardening — disable unused ports and services · change default passwords
- Network access control (NAC) — port security · 802.1X · MAC filtering
- Key management
- Security rules — access control list (ACL) · URL filtering · content filtering
- Zones — trusted vs. untrusted · screened subnet

---

## Device hardening

**Reducing a device's attack surface by removing what it does not need.** The principle: every enabled feature is a potential way in, so anything without a purpose gets turned off. This is the *default configuration is not a secure configuration* idea made concrete.

### Disable unused ports and services

Two different meanings of "port", and the exam uses both:

| Kind | Example | How it is disabled |
|---|---|---|
| **Physical port** | An empty switch port in the wiring closet | `shutdown` on the interface |
| **Logical port / service** | Telnet on 23, HTTP on 80, an unused management daemon | Stop the service, or block the port |

**A live switch port with no cable is a network jack for anyone who reaches it.** It hands out a lease, joins its VLAN, and forwards traffic — no authentication involved. The same logic applies to a running service nobody uses: it can still be exploited, still needs patching, and still appears in a scan.

**The counterargument is convenience**, and it is why this finding is so common: an administrator pre-configures ports for future use, and the future never audits them.

### Change default passwords

Default credentials for every consumer and enterprise device are published, searchable and indexed. Shodan and similar services list internet-exposed devices by model, which is enough to try the vendor default against them at scale.

**This extends past the admin login** — SNMP (Simple Network Management Protocol) community strings `public` and `private`, default wireless keys printed on a label, and vendor service accounts all count. **The Mirai botnet was built almost entirely on a list of about sixty default username/password pairs.**

## Network access control (NAC)

**Deciding whether a device is allowed onto the network at all, and enforcing that at the point where it connects.**

**⚠️ Not the same question a firewall answers.** A firewall controls **where an admitted device may go**. NAC controls **whether it gets admitted** — the port or the wireless association, before an address is even issued.

**Two timings, and the exam uses both terms:**

| | When the check happens |
|---|---|
| **Pre-admission** | **Before** access is granted. Fail and the device never reaches the network |
| **Post-admission** | **After** admission, on continued behaviour or a re-check. Fail and it is removed or quarantined |

**Posture assessment** is the health check some NAC systems apply — patch level, antivirus present and current, disk encryption, domain membership. **Agent-based** uses software on the endpoint; **agentless** infers what it can from the network. A device that fails is typically dropped into a **quarantine or remediation VLAN** with access to patch servers and nothing else.

**The objective names three enforcement mechanisms**, in increasing order of strength: MAC filtering, port security, and 802.1X.

### Port security

**A switch-port feature that limits which and how many MAC addresses may appear on a port.**

| Setting | Does |
|---|---|
| **Maximum** | How many MAC addresses the port may learn. **Default is 1** on Cisco |
| **Sticky learning** | Learn the address currently connected and write it into the running configuration, so it does not have to be typed |
| **Violation action** | What happens when a disallowed address appears |

**Three violation actions, and the difference is what you find out:**

| Action | Traffic | Logged | Port |
|---|---|---|---|
| `protect` | Dropped | **No** | Stays up |
| `restrict` | Dropped | **Yes** — SNMP trap and counter | Stays up |
| **`shutdown`** | Dropped | Yes | **`err-disabled`** — the Cisco **default** |

**⚠️ `protect` is the trap.** It enforces the policy and tells nobody, so a device that should not be there is silently blocked and no record exists. **Same failure shape as a drop rule with logging disabled.**

**`err-disabled` connects to objective 5.2.** A port in that state is down until an administrator clears it — `shutdown` then `no shutdown`, or an errdisable recovery timer. **"The port died and won't come back" is very often port security**, not a hardware fault.

**What it defends against:** an unauthorised device or a rogue hub or switch plugged into a wall port, and **MAC flooding**, since the port will not learn hundreds of addresses.

**⚠️ What it does not defend against: MAC spoofing.** An attacker who reads an allowed address and sets it on their own machine passes cleanly. **Port security proves which address is present, never which device.**

### 802.1X

**Port-based network access control, IEEE 802.1X.** The port itself stays shut to ordinary traffic until the device behind it **proves an identity**.

**Three roles, and the exam expects the names:**

| Role | Who | Does |
|---|---|---|
| **Supplicant** | The client device | Presents credentials |
| **Authenticator** | The **switch port** or the wireless access point | Holds the port closed and relays the exchange. **Decides nothing itself** |
| **Authentication server** | **RADIUS** (Remote Authentication Dial-In User Service) | Makes the decision |

**Two protocols, one on each side of the authenticator:**

```
supplicant  ←— EAPoL —→  authenticator  ←— RADIUS —→  auth server
```

**EAP** (Extensible Authentication Protocol) is a **framework rather than a method** — the method is chosen inside it. **EAPoL** is EAP over LAN, which is the only thing an unauthorised port will pass.

**Common methods:** **PEAP** and **EAP-TTLS** use a username and password inside a TLS tunnel. **EAP-TLS** uses **certificates on both ends** — the strongest, and the most work, because it needs a PKI (public key infrastructure).

**⚠️ This is the fix for port security's weakness.** Port security checks an address, which anyone can copy. **802.1X checks a credential**, which a spoofed MAC address does not provide.

**Dynamic VLAN assignment is the feature worth remembering.** RADIUS can return a VLAN along with the accept, so **the same physical port puts different users in different segments** by identity — and puts a failed posture check into a quarantine VLAN.

**Wireless uses the same mechanism.** WPA2-Enterprise and WPA3-Enterprise *are* 802.1X, as opposed to the Personal modes with one shared passphrase.

**⚠️ Devices with no supplicant are the practical problem** — printers, cameras, badge readers, most IoT. The usual answer is **MAB (MAC Authentication Bypass)**, which falls back to checking the MAC address against a list — **reintroducing exactly the weakness 802.1X was deployed to remove**, on the ports most likely to be physically accessible.

**And authorisation is per port, not per device.** A small switch or hub placed **behind** an authenticated machine rides on a port that is already open. **MACsec** (802.1AE) closes that by encrypting each link; 802.1X alone does not.

### MAC filtering

**An allow or deny list of MAC addresses**, applied on switch ports or — far more often — on a wireless access point. Only listed addresses may associate.

**⚠️ It is the weakest of the three, and the exam expects you to know why.**

**A MAC address is in the header of every frame, and headers are not encrypted** — not even on WPA2 or WPA3, where only the payload is. So an attacker within radio range **captures an allowed address without needing the network key at all**, then sets it on their own interface:

```
ip link set dev wlan0 address AA:BB:CC:DD:EE:FF
```

**Changing a MAC address takes one command and no privileges beyond local administrator.** There is no secret involved and nothing to verify — **the address is a claim, not a credential.**

**Where it is still reasonable:** as an administrative record of what is meant to be connected, or on segments where nothing better is available. **As a security control on its own it is a speed bump** — it deters a neighbour and stops nobody who is trying.

### The three compared

| | Checks | Defeated by | Strength |
|---|---|---|---|
| **MAC filtering** | An address against a list | **Sniffing and spoofing an address** | Weakest |
| **Port security** | Address **and count**, per port, with violation actions | Spoofing an allowed address | Middle |
| **802.1X** | **A credential** — password or certificate | Physical insertion behind a supplicant; MAB fallback | Strongest |

**The exam's tell:** a scenario where **an attacker captures traffic and then gains access** is pointing at MAC filtering. A scenario where **a port shuts itself down** is port security. A scenario naming a **RADIUS server, a supplicant, or certificates** is 802.1X.

**⚠️ And the shared limit worth stating: none of the three restrict what a device may reach once admitted.** That is the firewall's job, and a network that treats NAC as a substitute for segmentation has one control doing two jobs badly.

## Key management

**The lifecycle of cryptographic keys — everything around the encryption rather than the encryption itself.**

**⚠️ The algorithm is public; only the key is secret.** AES and RSA are published standards that anyone can read. **All of the security lives in the key**, which means it lives in how the key is generated, moved, stored, replaced and destroyed. **Strong encryption with careless key handling is not strong encryption.**

| Stage | The concern |
|---|---|
| **Generation** | Enough **randomness** and enough length. A predictable key defeats any algorithm |
| **Exchange / distribution** | **Getting the key to the other party without exposing it** — the oldest problem in cryptography |
| **Storage** | Where it rests, and what can read it |
| **Rotation** | Replacing it on a schedule |
| **Expiration** | A defined end of validity |
| **Revocation** | Cancelling it **before** expiry, when it is compromised |
| **Destruction** | Removing it, and every copy, at end of life |

**Exchange is the hard one, and it is what asymmetric cryptography exists to solve.** **Diffie-Hellman** lets two parties derive a shared secret over a channel an eavesdropper can read. **PKI** (public key infrastructure) solves the related trust problem — a certificate authority vouches that a public key belongs to who it claims.

**Storage, in roughly increasing strength:**

| Where | |
|---|---|
| **In application source code** | **The classic failure.** Once committed it is in the history forever, and rotating it is the only fix |
| A file on disk with restricted permissions | Adequate for low value |
| **Key vault / secrets manager** | Centralised, access-controlled, audited |
| **TPM** (Trusted Platform Module), **HSM** (Hardware Security Module), smart card | **The key never leaves the hardware** — it signs and decrypts on your behalf. Extraction requires physical attack |

**Rotation limits the blast radius in two directions**: it caps how long a stolen key stays useful, and it caps how much data a single key ever protected.

**Revocation is what makes expiry survivable early.** A certificate compromised today cannot wait for next year's expiry date — **CRL** (certificate revocation list) and **OCSP** (Online Certificate Status Protocol) are how clients learn it is no longer valid.

**Key escrow** is a deliberate copy held by a third party so data can be recovered if a key is lost. **It is a trade, not a feature** — recoverability bought with an extra copy of the secret, and an extra party who can read everything.

## Security rules

### Access control list (ACL)

**An ordered list of permit and deny statements**, evaluated **top to bottom**, where **the first match wins and evaluation stops.**

**Three properties carry most of the exam questions:**

**1 — Order decides the outcome.** A broad `permit` placed above a specific `deny` makes the deny **unreachable** — it can never be evaluated, and nothing warns you. The rule is not wrong; it is simply never reached.

**2 — There is an implicit `deny any any` at the end.** Anything not explicitly permitted is dropped. **An ACL with only `deny` statements and no permits blocks everything**, which is a classic way to remove a subnet from the network by accident.

**3 — It is applied to an interface in a direction.** `in` filters traffic entering the interface, `out` filters traffic leaving it. **The same list produces completely different results depending on which is chosen.**

**Two kinds, and where each belongs:**

| | Matches on | Place it |
|---|---|---|
| **Standard** | **Source address only** | **Close to the destination** — it cannot tell one service from another, so filtering early would block too much |
| **Extended** | Source, destination, protocol, port | **Close to the source** — it can be precise, so drop unwanted traffic before it crosses the network |

**Named or numbered** is presentation, not capability. Named lists can be edited line by line; numbered ones historically could not.

**⚠️ A router ACL is usually stateless.** It judges each packet alone and **knows nothing about connections** — so permitting outbound traffic does **not** permit the replies. Return traffic needs its own entry, or the `established` keyword matching packets with the ACK flag set.

**That is the line between an ACL and a stateful firewall.** A stateful firewall tracks the connection and permits replies automatically. **An ACL does not, which is why a one-line "permit outbound" rule often produces a network where nothing works.**

**ACLs are used well beyond filtering traffic** — restricting which addresses may reach a device's management interface, selecting routes for redistribution, and classifying traffic for QoS (quality of service). **The syntax is a matching language; filtering is just its most common use.**

### URL filtering

**Allowing or blocking web requests by address**, usually by **category** — gambling, adult, malware, social media — from a subscription feed the vendor maintains, plus local allow and block lists.

**Enforced at** a web proxy, a next-generation firewall, a DNS-layer service, or an endpoint agent.

**⚠️ HTTPS limits what can be seen without decryption.** In an encrypted session the path is invisible. What remains readable is the **domain**, from the **SNI** (Server Name Indication) field of the TLS handshake and from the server's certificate.

| Granularity | Needs |
|---|---|
| **Domain** — `example.com` | Nothing extra. SNI is in the clear |
| **Full URL** — `example.com/specific/page` | **TLS inspection** — the proxy terminates and re-encrypts the session |

**TLS inspection is an organisational decision, not a setting.** It requires the proxy's certificate authority to be trusted by every client, and it means **an appliance reads all of their traffic**, including banking and health sites, unless categories are deliberately exempted.

**Commonly bypassed by** a personal VPN, **DNS over HTTPS**, connecting to an address directly rather than by name, or a third-party proxy.

### Content filtering

**Inspecting what is being transferred rather than where it is going.**

| Filters on | Examples |
|---|---|
| **File type** | Block `.exe` and `.scr` downloads, or macro-enabled documents |
| **MIME type** | Block executables regardless of extension |
| **Keywords and patterns** | Card numbers or identifiers leaving the network — overlapping **DLP** (data loss prevention) |
| **Malware** | Scanning payloads and attachments |
| **Active content** | Stripping scripts before delivery |

**Enforced at** email security gateways, web proxies and next-generation firewalls.

**⚠️ The distinction the exam wants:**

| | Question it answers |
|---|---|
| **URL filtering** | **Where** are they going? |
| **Content filtering** | **What** is being transferred? |

**In products the terms blur** — "content filtering" is often used as the umbrella for both. **The examinable difference is address versus payload.**

**Both share one limit: encryption.** Neither can classify what it cannot read, so both are only as complete as the organisation's willingness to inspect TLS.

## Zones

**A zone is a group of interfaces or segments that share a trust level.** Policy is then written **between zones** rather than between individual interfaces — so adding a segment to an existing zone inherits the policy instead of needing its own rules.

### Trusted vs. untrusted

**The basic division**, and the default direction of suspicion:

| Zone | Typically |
|---|---|
| **Trusted** | The internal network — devices the organisation owns and manages |
| **Untrusted** | **The internet**, and anything not under organisational control |

**The default rule follows the trust gradient:** traffic from **untrusted to trusted is denied**, while **trusted to untrusted is generally permitted** — with replies allowed back by the firewall's state table rather than by a rule.

**⚠️ "Trusted" is relative, not a property of the network.** The label describes a policy decision, and treating an internal network as safe because it is internal is exactly the assumption **zero trust** rejects — where every request is authenticated and authorised regardless of where it originated.

### Screened subnet

**A separate segment for systems that must be reachable from the untrusted zone** — web, mail, DNS and VPN servers — placed so that it touches both sides and **belongs to neither**.

**This is the term CompTIA now uses for what was called a DMZ** (demilitarised zone). **Treat the two as the same thing**; older material and most products still say DMZ.

**The policy is the whole point:**

| From → To | |
|---|---|
| Untrusted → **screened subnet** | ✅ **Permitted**, on specific published ports only |
| Untrusted → trusted | ❌ **Denied** |
| **Screened subnet → trusted** | ❌ **Denied — this is the rule that matters** |
| Trusted → screened subnet | ✅ Permitted |

**⚠️ The design assumes the public server will eventually be compromised.** It is the most exposed thing the organisation runs. **The screened subnet's job is not to prevent that — it is to make it survivable**, by ensuring the attacker who succeeds lands somewhere that cannot reach anything internal.

**Two ways to build it:**

| | |
|---|---|
| **Three-legged firewall** | One firewall with three interfaces — untrusted, trusted, screened subnet. Cheaper, **one device to misconfigure or compromise** |
| **Back-to-back firewalls** | Two firewalls with the segment between them, ideally **from different vendors**, so one shared vulnerability does not open both |

**The exam's tell:** a scenario describing **public-facing servers isolated from internal systems** is a screened subnet, whichever name it uses.
