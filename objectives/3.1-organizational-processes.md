# 3.1 — Explain the purpose of organizational processes and procedures

## Documentation

### Physical vs. logical diagrams
Two views of the same network that answer different questions. Both are required, because **neither can represent what the other represents**.

**A physical diagram shows where equipment is and what it is plugged into** — devices in their actual locations, **port-to-port** connections (`IDF-2 / panel A / port 14 → switch 1 / ether14`), cable runs and types, and rack elevations. It is the document used when tracing a failed link by hand.

**A logical diagram shows how traffic moves** — IP addressing and subnets, VLAN boundaries, routing paths and gateways, firewall zones, and NAT boundaries. It is the document used to reason about *why* one host cannot reach another, a question that cable tracing cannot answer.

**⚠️ Each view hides exactly what the other reveals.** A single trunk cable appears on the physical diagram as one line; the several isolated VLANs it carries appear only on the logical diagram. Conversely, two segments drawn as entirely separate on a logical diagram may share one physical wire.

| | Shows | Hides |
|---|---|---|
| **Physical** | The cable, the port, the rack unit | That one cable carries several isolated networks |
| **Logical** | Segments, subnets, routing paths | That those segments share a single wire |

**The failure mode is documentation drift.** Both diagrams become inaccurate as soon as a port is re-patched or a VLAN is added, and a confidently wrong diagram is worse than none — it directs troubleshooting away from the fault. The controls are to **date and version them, and to update them as part of the change itself** rather than afterwards, which is why documentation and change management appear in the same objective.

### Rack diagrams
An **elevation view of a single rack**, recording what occupies each rack unit.

**What it records:** device name and model per U, the **U position and height** of each device (`U20–U21` for a 2U server), **separate front and rear views**, which **PDU and circuit** each device draws from, and often weight and heat output.

**Its purpose is capacity planning without a site visit.** "Will this 2U server fit, and is there power for it?" is answerable from the diagram — including the case where the answer is *no* because the free space exists as scattered 1U gaps rather than two contiguous units. It also carries forward the physical decisions from objective 2.4: rack units, depth, weight distribution, blanking panels, and airflow direction.

**⚠️ Rack diagrams drift more than most documentation**, because racks are physically accessible and a device can be added during an incident without anyone updating a drawing. The consequence is capacity planning against fiction — buying hardware for space that no longer exists, or leaving a circuit overloaded because the diagram reports it at 60%.

**The rear view is the commonly omitted half**, and it is the half showing power distribution and airflow direction — the two factors most likely to cause a problem.

### Cable maps and diagrams
Where a rack diagram records what is **inside** a rack, a **cable map** records the runs **between** locations — particularly those concealed in walls, ceilings, and risers.

**Recorded per permanent run:** the **cable ID** matching its physical label, **both endpoints** (`Room 214 outlet B ↔ IDF-2 / panel A / port 14`), cable type and category, length, install date, and certification test results.

**⚠️ It exists because an in-wall cable cannot be traced.** A run disappears into a wall at one end and emerges elsewhere; without the map, locating it requires a **toner and probe** or opening ceilings. The map is the only inexpensive answer, which is a different situation from a rack, where a cable can at least be followed by hand.

**The scope distinction that matters:**

| | Documented by | Rate of change |
|---|---|---|
| **Permanent link** — outlet to patch panel | **Cable map** | Almost never |
| **Patch cord** — panel to switch port | Port assignment records / IPAM | Constantly |

**Cable maps document what does not change.** This is precisely why the patch panel exists (objective 2.4) — the stable half of the path is mapped, and the volatile half is tracked elsewhere. Attempting to map patch cords produces documentation that is inaccurate within days.

**Labelling is the inseparable other half.** A cable map is unusable unless the physical cables carry matching labels, applied at **both ends** — locating one end of an unlabelled run reveals nothing about the other.

**Note the term is ambiguous.** A *cable diagram* may instead mean a **wiring or pinout diagram** — the **T568A / T568B** pin assignments consulted before terminating a jack, rather than a record of where runs go.

### Network diagrams — Layer 1, Layer 2, Layer 3
The same devices appear at every layer, but **a line between them means something different at each**.

| | Shows | A line represents | Answers |
|---|---|---|---|
| **Layer 1** | Cables, ports, media types, patch panels | **A cable** | What is physically connected? |
| **Layer 2** | Switches, VLANs, trunk vs. access ports, spanning tree, link aggregation | **A VLAN or trunk relationship** | Which broadcast domain, and what is the loop-free path? |
| **Layer 3** | Subnets, gateways, routers, firewalls, routing protocols, NAT boundaries | **A routed adjacency** | How does a packet reach another subnet? |

**Each layer multiplies what the one below carries.** A single trunk cable is one line at Layer 1; the several VLANs it carries are separate segments at Layer 2; and those become distinct routed subnets with policy between them at Layer 3. None of that is visible from the Layer 1 view.

**⚠️ The common documentation error is mixing layers on one diagram** — adding VLAN identifiers, then subnets, then firewall zones to a cable drawing. The result is cluttered and answers no question cleanly.

**Choosing which to open is a troubleshooting heuristic:**

| Symptom | Diagram |
|---|---|
| Link down, no indicator lights | **Layer 1** |
| Link up but in the wrong broadcast domain, or a loop | **Layer 2** |
| Local subnet reachable, another subnet not | **Layer 3** |

**The layer at which the symptom appears identifies the diagram to consult** — the same layered reasoning used for encapsulation in objective 1.1, applied to documentation.

### Asset inventory
An **authoritative record of what the organisation owns and runs**, carrying enough detail to make decisions about each item.

**⚠️ It is the foundational control, not administrative overhead.** Hardware and software inventory are **CIS Controls #1 and #2**, ahead of firewalls and encryption, because every other control assumes you know what you are protecting. When a critical **CVE** is published, the only question that matters is *"do we run that, and where?"* — an organisation without an inventory is exposed for however long the answer takes to assemble.

| Category | Records | Consequence of not having it |
|---|---|---|
| **Hardware** | Make, model, **serial number / service tag**, location by rack and U, MAC addresses, purchase date, owner | Cannot locate it, claim warranty, or plan replacement |
| **Software** | Applications and **versions**, operating system and patch level, **firmware** versions | Cannot answer whether a published vulnerability applies |
| **Licensing** | Entitlements, seat counts, keys, **renewal dates** | Audit exposure, or paying for unused seats |
| **Warranty support** | Coverage dates, support tier, SLA level | Discovering coverage lapsed **after** a failure |

**⚠️ Licensing fails in both directions.** Being **under-licensed** creates legal and audit exposure with real financial penalties; being **over-licensed** means paying annually for seats nobody uses or support contracts on decommissioned equipment. Both arise from the same cause — nobody knows the true count.

**Warranty status is a risk decision rather than paperwork.** A device out of warranty is a device the organisation is **self-insuring**. Knowing this in advance allows a deliberate choice — stock a spare, accept the risk, or renew — whereas discovering it during an outage means the choice was made by default.

**The recurring failure is drift and shadow IT.** A manually maintained spreadsheet becomes inaccurate within weeks and never contains devices nobody reported. **Automated discovery** through network scanning and endpoint agents finds what people omit, including equipment that should not be present at all.

### IP address management (IPAM)
A system for **planning, tracking, and managing IP address space** — which addresses are allocated, to what, and in which subnet.

**What it tracks:** subnets and their purpose, allocated versus free addresses, static assignments and their owners, DHCP scopes and reservations, VLAN association, and hostname/DNS mapping.

**⚠️ The primary failure it prevents is the duplicate address conflict.** Two administrators assign the same static address, and both hosts develop intermittent connectivity that presents as a hardware fault. The specific case worth recognising is a **static assignment made inside the DHCP pool** — it works perfectly until the DHCP server issues that address to another device, at which point both fail apparently at random. This is why the boundary between DHCP-managed and statically assigned space must be documented and enforced.

**Three further failures:**
- **Subnet exhaustion** — running out of addresses with no warning, because utilisation was never tracked.
- **Orphaned allocations** — addresses still reserved for systems decommissioned years earlier, quietly reducing usable space.
- **Unanswerable questions** — identifying what a given address belongs to should take seconds; without IPAM it requires a packet capture and inference.

**DDI** is the common deployment: **DNS + DHCP + IPAM** integrated, because the three share the same underlying truth. DHCP issues an address, DNS must resolve the matching name, and IPAM must record both — managed separately they drift apart. Tools include **phpIPAM**, **NetBox**, Infoblox, and BlueCat.

**IPv6 makes IPAM mandatory rather than convenient.** A spreadsheet is workable for a single /24; it is not workable for IPv6, where the address space is too large to reason about and individual addresses are not memorable enough to recognise by sight.

### Service-level agreement (SLA)
A **contract defining the level of service expected**, how it is measured, and what happens when it is not met.

**Availability is expressed in "nines":**

| Availability | Downtime per year | Downtime per month |
|---|---|---|
| **99%** | 3.65 days | 7.2 hours |
| **99.9%** (three nines) | 8.77 hours | 43.8 minutes |
| **99.99%** (four nines) | 52.6 minutes | **4.38 minutes** |
| **99.999%** (five nines) | **5.26 minutes** | 26 seconds |

**Each additional nine reduces permitted downtime by roughly 90% and multiplies cost.** Five nines allows 26 seconds per month, which excludes any process requiring a human to notice and respond.

**⚠️ Response time is not resolution time** — the distinction this objective most often tests.

| Term | Meaning |
|---|---|
| **Response time** | How quickly the provider **acknowledges** the issue |
| **Resolution time** | How quickly it is actually **fixed** |

**Many agreements guarantee only response.** A one-hour response SLA is satisfied by a callback within the hour while the outage continues indefinitely.

**Other components:** **MTTR** (mean time to repair), **MTBF** (mean time between failures), service credits, scope and exclusions, and the measurement method — who measures, and over what window.

**⚠️ Three provisions that quietly weaken an agreement:**
- **Scheduled maintenance is normally excluded**, so a stated 99.99% can coexist with a four-hour monthly window that does not count against it.
- **Service credits are capped**, typically at a fraction of the monthly fee. An outage costing far more than the service fee is not compensated — **an SLA is an incentive, not insurance.**
- **Credits generally must be claimed** rather than being applied automatically, and claim windows expire.

**Note that residential internet service carries no meaningful SLA** — it is best-effort, with no uptime guarantee and no credits. That is the binding availability constraint on any service hosted behind one.

### Wireless survey / heat map
A **survey** measures RF conditions in a physical space; a **heat map** is its visual output — a floor plan overlaid with colour representing signal strength and related metrics.

| Survey type | Method | Accuracy |
|---|---|---|
| **Predictive** | Software model using an imported floor plan and specified wall materials; no site visit | Lowest — a simulation |
| **Passive** | Walking the site **listening**, without associating to the network | Real measurements of signal and interference |
| **Active** | **Associating a client** and walking, measuring throughput, retries, and roaming behaviour | Highest — reflects actual user experience |

**Passive describes the radio environment; active describes what a user experiences within it.** The two differ, which is why both are performed.

**AP-on-a-stick** is the intermediate validation step — temporarily mounting an access point on a tripod at a proposed location to confirm a predicted design before permanent installation.

**A heat map reveals** coverage gaps, over-coverage, channel overlap between neighbouring access points, and interference from non-Wi-Fi sources.

**⚠️ Uniformly strong signal is not the objective.** A heat map showing strong coverage everywhere indicates **over-coverage**, which produces **sticky clients** — devices retaining a distant access point because its signal remains adequate — and **co-channel interference** between access points that can hear one another. The goal is appropriate coverage with **distinct cell boundaries**, not maximum signal strength.

**Its place in a documentation objective is as the baseline.** Without a survey on record, a complaint that wireless performance has degraded cannot be tested against anything. Surveys are therefore performed **twice**: before deployment to design it, and after to validate it.

**⚠️ Surveys have a shelf life.** RF conditions change with new interior walls, neighbouring access points, metal furniture, and occupancy — **human bodies are largely water, which absorbs 2.4 GHz effectively**, so a survey of an empty room does not describe that room in use.

## Life-cycle management

### End-of-life (EOL) and end-of-support (EOS)
Two vendor-published dates that are **not** the same date.

| | **EOL — end of life** | **EOS — end of support** |
|---|---|---|
| Vendor ceases | **Selling** the product; no new features | **All** support — patches, security updates, assistance, RMA |
| Device still functions | Yes | **Yes** |
| Device still defensible | Yes | **No** |
| Sequence | **First** | **Later**, often by years |

**EOL is an announcement; EOS is the cliff.** The interval between them is the planning runway the vendor provides.

**⚠️ After EOS, every newly discovered vulnerability in the product is permanent.** No patch will be issued. The equipment continues performing its function while accumulating unfixable weaknesses, and **nothing breaks** — there is no outage or alert to force action, which is precisely what makes it dangerous.

**Compliance frameworks treat it as a finding in itself.** PCI DSS, HIPAA, and most others require supported software, so running past EOS can fail an audit regardless of whether anything was exploited.

**Life-cycle management depends on asset inventory.** Tracking these dates requires knowing what equipment exists and what version each item runs — an organisation unable to report the firmware on a given switch cannot know whether that switch is supported.

**⚠️ The IoT case is the sharpest example.** Inexpensive connected devices frequently reach EOS within a year or two, sometimes with no announcement, are rarely inventoried, often cannot be updated at all, and remain installed for years. Since they cannot be patched, they must instead be **contained** — which is the actual justification for placing them in an isolated VLAN. **Segmentation is the compensating control for equipment that cannot be fixed.**

### Software management
Keeping software current and controlled across three layers that carry **very different levels of risk**.

**Patches and bug fixes.** A **security patch** addresses a vulnerability, a **bug fix** addresses a functional defect, and a **feature update** adds capability — three categories with different risk profiles and often different approval paths. The cycle is **identify → test → deploy → verify**.

**⚠️ The governing tension is speed against safety.** Patching quickly closes the vulnerability window; patching slowly avoids breaking production. Both are correct and they conflict, and the surrounding process exists to manage that conflict:
- **Test in a non-production environment first** — patches break things routinely
- **Establish a rollback plan** before deploying
- **Patch Tuesday** — Microsoft's second-Tuesday cadence — exists so organisations can plan; the predictability is the point
- **Out-of-band patches** bypass the normal cycle when a vulnerability is being actively exploited
- **Maintenance windows** provide the scheduled downtime, which is also what SLA availability calculations exclude

**Operating system.** Version and patch level are tracked separately, since a major version upgrade and a security patch differ in risk. **OS end-of-support is the one deadline that cannot be rescheduled.**

**⚠️ Firmware is the highest-risk category.** It is software embedded in hardware — switches, routers, access points, **BIOS/UEFI**, drive controllers, and network adapters. **A failed OS patch means a reboot or a restore; a failed firmware update can render the device permanently unusable**, because there may be no operating system beneath it to recover from.

The requirements follow directly: **uninterrupted power** during the flash, the **correct image for the exact model and architecture**, no interruption once started, and **correct ordering** where several components update — an operating system image is normally applied and rebooted before its bootloader, since the bootloader update expects the new version already to be running.

**Firmware is neglected because it is invisible.** An operating system prompts for updates; firmware remains at whatever version shipped and says nothing. It also sits **below the operating system**, meaning firmware vulnerabilities are beneath the layer at which endpoint protection, logging, and access controls operate — those controls cannot observe it and therefore cannot mitigate it.

### Decommissioning
The **controlled removal of a system from service** — a defined process rather than simply disconnecting equipment.

**The sequence:** identify dependencies (DNS records, firewall rules, monitoring checks, scripts, DHCP reservations, certificates, licences) → back up or archive, since retention requirements often outlive the hardware → **sanitise the data** → remove from inventory, IPAM, monitoring, and documentation → reclaim licences → dispose.

**Data sanitisation methods, and what each actually works on:**

| Method | Mechanism | ⚠️ Limitation |
|---|---|---|
| **Overwriting / wiping** | Writes patterns over stored data | **Unreliable on SSDs** — wear levelling means the controller may never overwrite the original cells |
| **Cryptographic erase** | Destroys the key on a self-encrypting drive | Requires the drive to have been encrypted from the outset |
| **Degaussing** | A magnetic field disrupts the media | **Has no effect on an SSD**, which has no magnetic domains |
| **Physical destruction** | Shredding, crushing, incineration | Most certain; eliminates resale value |

**The distinction to remember: degaussing and overwriting were designed for magnetic media.** For solid-state storage, use **cryptographic erase or physical destruction**.

A **certificate of destruction** provides documented proof from the disposal vendor, and **chain of custody** records who held the device between removal and destruction. Both exist to satisfy audit requirements.

**⚠️ The networking failure is the dangling reference.** Data recovered from resold drives is the widely known risk, but the more common operational failure is removing a device without removing what points at it:

| Left in place | Consequence |
|---|---|
| **DNS record** | The address is reassigned and traffic reaches the **wrong host** |
| **Firewall rule** | Access is now permitted to whatever next holds that address |
| **Monitoring check** | Permanent alerts for a device that no longer exists, producing alert fatigue |
| **IPAM entry** | Never released — the **orphaned allocation** described under IPAM |

**The equipment is gone; the permissions granted to it are not.** This is why dependency identification is the first step rather than an afterthought — those references become invisible once the hardware has been removed.

## Change management

The formal process for **proposing, reviewing, approving, implementing, and documenting changes** to a system.

**⚠️ Its justification is that most outages are caused by changes** — not by hardware failure or attack. Change management is a control on the single largest source of unplanned downtime rather than administrative overhead.

**The sequence:** request → assess → approve → schedule → implement → verify → document → close. Significant changes are approved by a **CAB (change advisory board)**.

**A change request contains:** what is changing and why, a **risk assessment**, the **impact** on users and systems, a **rollback plan**, a testing plan, the **maintenance window**, and the approver.

**The rollback plan is the non-negotiable element** — an inability to describe how a change would be reversed indicates it is not ready to be made.

| Change type | Approval | Example |
|---|---|---|
| **Standard** | **Pre-approved** — routine and low risk | Adding a user; applying a known-good template |
| **Normal** | Full process with CAB review | Firmware upgrade, new VLAN |
| **Emergency** | **Expedited** for an outage or active incident | Blocking an attacking address |

**⚠️ Emergency changes are still documented, retroactively.** Omitting the record because the change was urgent is how documentation diverges from reality, and urgent changes are the ones most worth having recorded.

### Request process tracking / service request

| | Definition | Example |
|---|---|---|
| **Service request** | A routine, **pre-approved** request for something | New laptop, password reset, access grant |
| **Change request** | A **modification to infrastructure** | New firewall rule, switch replacement |

Both are tracked in a ticketing system, which supplies the audit trail: **who requested, who approved, who implemented, when, and what resulted.**

**The payoff appears in troubleshooting.** *"What changed?"* is the first question in most outages, and change records are what make it answerable — without them, recent history has to be reconstructed from memory. **The documentation step is the one most often skipped**, and it is the one that matters months later when nobody recalls why a rule exists.

## Configuration management

Tracking and controlling the **actual settings** of devices and systems. **Change management governs the process of making a change; configuration management governs the resulting state** — change is the verb, configuration is the noun.

### Production configuration
The configuration **currently running on the live device**.

**⚠️ On network equipment this exists in two forms**, and the gap between them causes a common failure:

| | Stored in | Currently active |
|---|---|---|
| **Running config** | RAM | **Yes** |
| **Startup config** | NVRAM | Loads at next boot |

**A change made to the running config but never saved is lost at the next reboot** — frequently discovered weeks later during unrelated maintenance, when the device reverts to a configuration nobody remembers. The inverse is worse: a **faulty configuration that has been saved** survives every attempt to reboot out of it.

### Backup configuration
A copy stored **off the device**, from which it can be restored.

**⚠️ A backup stored on the device is not a backup** — if the device fails, the copy fails with it. This is violated routinely because the equipment has ample flash storage and saving locally feels sufficient.

**Three requirements:** stored **off-device**; **versioned**, so the configuration from before a specific change is recoverable rather than only the most recent copy; and **restore-tested**, since an untested backup is an assumption rather than a control. Storing exported configurations in version control satisfies all three.

### Baseline / golden configuration

| Term | Meaning |
|---|---|
| **Baseline** | The documented **standard state** a device is expected to be in |
| **Golden configuration** | The **master template** from which new devices are built |

**Their purpose is consistency** — every device in a given role begins identical, so that differences between them are meaningful rather than accidental.

**Configuration drift** is the divergence of devices from that baseline through undocumented ad-hoc changes. Detecting it means comparing running configuration against the baseline.

**⚠️ Drift detection is also a security control.** An unexpected difference is either an undocumented change or an intrusion, and the two are indistinguishable until investigated — which makes configuration comparison a detection capability rather than only a hygiene measure.

**⚠️ "Baseline" is an overloaded term.** A **configuration baseline** is the known-good settings described here; a **performance baseline** is normal traffic and utilisation levels used to identify anomalies, covered in objectives 3.2 and 5.4. The exam uses both senses.

**Distinguishing the two in practice: a baseline is what devices are audited *against*; a golden configuration is what they are deployed *from*.**

| | **Baseline** | **Golden configuration** |
|---|---|---|
| Nature | A **standard / compliance target** | A **complete deployable template** |
| Contents | Mandatory settings only — a **subset** | The **entire** configuration |
| Direction of use | Existing device **compared to** the baseline | Golden config **pushed to** a new device |
| Question answered | "Does this device meet our standard?" | "What configuration does this new switch receive?" |
| Frequency | Continuously, to detect drift | Once, at build time |

**A baseline for an access switch** might mandate only: SSH enabled with telnet and HTTP disabled, the default password changed, NTP and syslog pointed at known servers, native VLAN set to an unused ID rather than VLAN 1, DTP disabled on access ports, BPDU Guard enabled, and unused ports shut down. Every access switch either satisfies those points or does not. **It deliberately says nothing about which VLANs exist or what the device's address is**, because those differ per device and therefore cannot form part of a shared standard.

**A golden configuration for the same switch** is a complete file — identity, credentials, NTP and logging targets, the bridge with VLAN filtering enabled, the full VLAN table, every port's PVID and trunk definition, and the entire firewall rule set — loaded onto new hardware and then customised only for hostname and management address.

**The golden configuration satisfies the baseline by construction**, so a device built from it passes the audit on day one. **Drift is everything that happens afterwards**, and the baseline is the instrument that detects it.

**⚠️ The terms blur in ordinary usage**, and many organisations maintain a single artifact serving both purposes. CompTIA lists them as one bullet, so the testable idea is that a known-good reference exists and that deviation from it is detectable — not the precise boundary between the two words.
