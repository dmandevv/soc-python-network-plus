# 1.6 — Compare and contrast network topologies, architectures, and types

## Topologies

### Mesh
Every node connects to multiple other nodes, so traffic has **several possible paths** between any two points. In a **full mesh** every node connects to every other; in a **partial mesh** only some do.

**Its property is resilience:** losing a link or a node removes one path, not connectivity — traffic reroutes automatically. That makes it the topology for anything that must not go down.

**Its problem is that links grow quadratically.** A full mesh of *n* nodes needs **n(n−1)/2** links:

| Nodes | Links |
|---|---|
| 4 | 6 |
| 10 | **45** |
| 50 | **1,225** |

That is why full mesh is confined to small numbers of critical nodes — WAN cores, ISP peering — and **partial mesh** is what real networks use: full redundancy where it matters, single paths where it does not.

**Wireless mesh** is the same idea applied to access points relaying through each other, useful where running cable to every AP is impractical. Each wireless hop costs throughput, since the radio repeats traffic rather than forwarding it on a separate medium.

### Hybrid
Any combination of two or more topologies in one network — and **it is what essentially every real network is**, because different parts of a network have different requirements.

**The canonical example — a typical enterprise:**
- **Star** at the access layer: each workstation has a single cable back to a switch
- **Partial mesh** between core switches: redundancy where an outage would be expensive
- **Point-to-point** for WAN links to branch offices

**Why it exists:** applying one topology uniformly is either wasteful or fragile. Full mesh to every desk is absurd; a single path between data centres is reckless. Hybrid means matching the topology to what each segment actually needs.

**Exam framing:** if a scenario describes a network using more than one topology — which describes almost any realistic one — hybrid is the answer. "Star-bus" and "star-ring" are older named hybrids you may still see.

### Star / hub and spoke
Every node connects to a **single central device** — a switch on a LAN, a headquarters router on a WAN. Nodes do not connect to each other; all traffic passes through the centre.

**Why it dominates LAN wiring:** a failed cable or port affects **exactly one device**. Adding a node means running one cable. Troubleshooting is straightforward because every path is independent. This is what replaced the coaxial bus, where a single break took down the whole segment.

**Its weakness is the obvious one: the centre is a single point of failure.** Lose the switch and everything attached to it is isolated — which is why distribution and core layers add redundancy while the access layer stays a simple star.

**Hub and spoke** is the same shape applied to WANs: branch offices (spokes) all connect to headquarters (hub). Cheap and simple, but **branch-to-branch traffic must traverse the hub**, adding latency — and if the hub link fails, the branch is cut off entirely. That inefficiency is a large part of what SD-WAN and partial-mesh WAN designs exist to fix.

### Spine and leaf
A two-tier data centre design where **every leaf switch connects to every spine switch**, and **leaves never connect to each other**. Servers attach only to leaves; spines exist purely to interconnect leaves.

**Its defining property is a predictable path length:** any server reaches any other server in **exactly two hops** — leaf → spine → leaf. No path is longer than another, so latency is consistent regardless of which racks are involved.

**Why it replaced three-tier in data centres:** traffic patterns changed. Three-tier was built for **north-south** traffic (users reaching servers), where an oversubscribed path upward is acceptable. Virtualization, microservices, and distributed storage made most traffic **east-west** (server to server), which three-tier handles badly — two servers in adjacent racks might traverse access → distribution → core → distribution → access.

**Scaling is linear and non-disruptive:** more capacity between racks means adding a spine; more server ports means adding a leaf. Neither requires redesigning the fabric.

**It also removes STP from the fabric.** Every leaf-spine link is active simultaneously using ECMP (equal-cost multi-path) at Layer 3, rather than STP blocking redundant paths and wasting them.

### Point to point
The simplest topology: **exactly two endpoints connected by a dedicated link**, with no other device sharing it. All bandwidth belongs to those two nodes.

**Where it appears:**
- A **WAN circuit** between two sites (leased line, Direct Connect, dark fiber)
- A **wireless bridge** between two buildings, using directional antennas
- A **switch-to-switch uplink**
- A **serial/console** connection for out-of-band management

**Why it matters conceptually:** every full-duplex switched Ethernet link is technically point to point — which is what eliminated collisions. It is also the "segment" from STP: in a modern switched network, each cable is its own point-to-point segment, and that is why RSTP can transition ports to forwarding almost instantly on links it knows are point to point rather than shared.

**Its tradeoff is cost against dedication:** guaranteed bandwidth and predictable latency, but the link serves only two endpoints and provides no redundancy of its own.

## Architectures

### Three-tier hierarchical model — Core
The **backbone** of the three-tier design. Its single job is moving large volumes of traffic between distribution blocks **as fast as possible**.

**Design principle: do nothing that slows it down.** No access control lists, no filtering, no policy, no QoS classification — those belong at distribution. The core forwards, and nothing else.

**Its characteristics:**
- **Highest throughput** hardware in the network
- **Fully redundant** — every core device and link duplicated, since a core failure affects everything
- **Layer 3** switching between distribution blocks
- Few devices, few connections, no end users or servers attached directly

**Why keep it simple:** every feature enabled at the core is applied to *all* traffic in the network. A filtering rule that costs microseconds at the access layer costs the same microseconds on every packet the organization sends. Complexity also means more configuration to get wrong in the one place where a mistake is total.

### Three-tier hierarchical model — Distribution
The **policy layer**, sitting between access and core. This is where the network makes decisions rather than simply forwarding.

**What it does:**
- **Inter-VLAN routing** — the boundary between Layer 2 below and Layer 3 above
- **Access control lists** and security policy enforcement
- **QoS classification and marking**
- **Route summarization**, so the core sees a few aggregate routes rather than hundreds of specific ones
- **Redundancy for the access layer** — each access switch uplinks to two distribution switches
- **First-hop redundancy** (HSRP/VRRP) providing a resilient default gateway

**Why policy belongs here:** it is the aggregation point. Rules applied at distribution cover every access switch beneath it, so you configure once instead of per closet — and the core stays free to forward at line rate.

**Route summarization matters more than it sounds:** without it, every access subnet appears individually in the core's routing table. Summarizing at distribution keeps core tables small, speeds convergence, and prevents a flapping access link from rippling instability into the backbone.

### Three-tier hierarchical model — Access
The layer **end devices actually plug into** — workstations, printers, phones, access points, cameras. Highest port count, lowest cost per port, and the layer users physically interact with.

**What it does:**
- **Port density** — the bulk of the network's switch ports live here
- **VLAN assignment** — access ports placed in their appropriate VLAN
- **PoE** for phones, APs, and cameras
- **Port security**, **802.1X**, and **MAC filtering** — the network access control edge
- Layer 2 switching, with uplinks to two distribution switches for redundancy

**Why security enforcement starts here:** this is the only layer an attacker can physically reach. Everything above it is in a locked room; access ports are in cubicles, lobbies, and meeting rooms. 802.1X and port security exist because an unattended wall jack is the easiest way into a network.

**Its redundancy model differs deliberately:** individual access switches are *not* duplicated, because a failure affects one closet rather than the organization. The redundancy is in each switch having **two uplinks** to different distribution switches — protecting the path, not the box.

**The division of labour across all three:** *Access connects. Distribution decides. Core forwards.*

### Collapsed core
A **two-tier** design that merges the core and distribution layers into a single tier, leaving access below it. Also called **collapsed backbone**.

**Why it exists:** three separate tiers only pay off at scale. For a single building or a small campus, a dedicated core forwarding between two distribution blocks adds cost, latency, and devices to manage while solving a problem that does not exist yet. Merging them removes a hop and a hardware tier.

**Where it fits:** small and mid-sized networks, single-site organizations, branch offices. Modern switches are also fast enough that one device comfortably handles what previously needed two tiers.

**What is kept and what is lost:** the *functions* all remain — inter-VLAN routing, ACLs, QoS, redundancy — they simply run on one tier instead of two. What is lost is **independent scaling**: growing beyond the collapsed pair's capacity means replacing it rather than adding a distribution block beside it.

**Redundancy still matters:** a collapsed core is normally a **pair** of switches, not one. Merging tiers should not mean merging away the redundancy, since that single tier now carries everything the core and distribution both used to.

## Traffic flows

The names come from how network diagrams are drawn — external networks at the top, internal systems arranged horizontally below.

### North-south
Traffic moving **into or out of** the data centre or network — vertically on a diagram. A user on the internet reaching a web server, a workstation querying an external DNS server, a backup uploading to cloud storage.

**Why it matters for design:** north-south traffic crosses the **security perimeter**, so it passes firewalls, IDS/IPS, proxies, and NAT. That is where traditional perimeter security concentrates, because it is where trusted meets untrusted.

**It is what three-tier was built for.** The hierarchy assumes traffic flows upward from access toward the core and out, which is why oversubscription increases at each layer — most traffic was expected to be leaving.

### East-west
Traffic moving **between systems inside** the data centre or network — horizontally on a diagram. A web server querying a database, replication between storage nodes, microservices calling each other, VM live migration.

**It became the dominant flow.** Virtualization, microservices, and distributed storage mean one external request often triggers many internal ones — a single page load fanning out to a dozen backend services. In modern data centres east-west traffic vastly exceeds north-south.

**Two consequences:**

**Architecture** — three-tier handles east-west badly, since two servers in adjacent racks may traverse access → distribution → core → distribution → access. **Spine-and-leaf** was designed for it: any server reaches any other in two hops.

**Security** — perimeter defences inspect north-south traffic and never see east-west at all. An attacker who gets inside moves laterally through traffic no firewall is watching. That gap is the entire argument for **microsegmentation** and **zero trust architecture** (Objective 1.8): stop treating "inside" as trusted, and inspect east-west as rigorously as north-south.

| | **North-south** | **East-west** |
|---|---|---|
| Direction | In/out of the network | Between internal systems |
| Crosses perimeter | **Yes** | **No** |
| Inspected by edge security | Yes | **Usually not** |
| Architecture suited to it | Three-tier | **Spine-and-leaf** |
| Security concern | External attack | **Lateral movement** |
