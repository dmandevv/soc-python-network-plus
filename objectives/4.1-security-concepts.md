# 4.1 — Explain the importance of basic network security concepts

## Logical security

### Encryption — data in transit vs. data at rest

| | **Data in transit** | **Data at rest** |
|---|---|---|
| Protects data while it is | **Crossing a network** | **Stored on a medium** |
| Typical mechanisms | TLS, IPsec, SSH, WPA3 | BitLocker, LUKS, database and backup encryption |
| Threat it defeats | **Interception** — on-path attacks, sniffing, a tapped link | **Physical loss** — a stolen laptop, disk, or backup tape |
| Where protection ends | **At the endpoints** — decrypted on arrival | **At boot and login** — decrypted once the system is running |

**They defend against different threats, and neither substitutes for the other.** This is the whole point of listing both.

- Full-disk encryption protects a laptop that is **switched off and stolen**. It gives you nothing against an attacker who has a logged-in session — the operating system hands them plaintext, because that is its job.
- TLS (Transport Layer Security) protects the wire and says nothing about what the server does with the data after it arrives. A site can have flawless HTTPS and still store passwords in a plaintext database.

**⚠️ Watch for scenario questions that describe one threat and offer the other control.** "Backup tapes went missing in transit between sites" is a data-at-rest problem despite the word *transit* — the tapes are storage media, not a network flow. "Credentials captured on guest Wi-Fi" is data in transit despite involving stored credentials.

**Data in use** — data decrypted in memory while being processed — is the third state, and is the hardest to protect. It is **not** in the N10-009 objectives, but it explains why the other two have hard limits: everything must become plaintext somewhere in order to be useful.

*Homelab: WireGuard in Phase 2 is a data-in-transit control. It protects the tunnel, not the Proxmox disks at either end.*

### Certificates

A **digital certificate binds an identity to a public key**, and an issuer signs that binding. The identity is a name — a domain, a device, a person. Everything about certificates follows from asking *who vouched for this binding, and do I trust them?*

#### Public key infrastructure (PKI)

| Component | Role |
|---|---|
| **Root CA** | The trust anchor. Self-signed by definition — the chain has to stop somewhere. Kept offline |
| **Intermediate CA** | Issues day-to-day certificates so the root stays offline. Compromise here is survivable |
| **End-entity certificate** | The one on your web server or VPN gateway |
| **CSR** | Certificate Signing Request — sent to the CA, containing your public key and name |
| **CRL / OCSP** | How a certificate is revoked before it expires |

**Trust is not in the certificate — it is in the trust store.** The operating system and browser ship with a list of root CAs they accept, and a certificate validates if a chain can be built from it up to something already in that store. This is why an organisation can run an internal CA: push the internal root into every managed machine's trust store and internally issued certificates validate cleanly.

#### Self-signed

Issuer and subject are the same entity. Nobody independent vouches for it.

**⚠️ Self-signed does not mean weaker encryption.** The cipher suite, key length, and TLS session are identical to a paid certificate. The **only** thing missing is third-party identity verification.

Legitimate uses: internal appliance management pages, lab systems, anything where the fingerprint can be verified by hand. It fails publicly because a visitor cannot distinguish a self-signed certificate from an attacker's.

**⚠️ Expired certificates are a top troubleshooting scenario.** The symptom is a service that worked yesterday and now fails for every user at once, with browser trust errors.

*Homelab: Proxmox and RouterOS both present self-signed certificates by default — that is the browser warning. Encryption is fine; the warning is about identity.*

### Identity and access management (IAM)

IAM answers two separate questions, and the objectives split them deliberately:

- **Authentication** — *are you who you claim to be?*
- **Authorization** — *given that you are, what may you do?*

A user who logs in successfully but gets "access denied" opening a share has **passed authentication and failed authorization**.

#### Multifactor authentication (MFA)

| Factor | Meaning | Examples |
|---|---|---|
| **Something you know** | Knowledge | Password, PIN, security question |
| **Something you have** | Possession | Hardware token, smart card, phone with an authenticator app |
| **Something you are** | Inherence | Fingerprint, face, retina, voice |
| **Somewhere you are** | Location | Source IP, GPS, geofence |
| **Something you do** | Behaviour | Typing rhythm, gait, signature dynamics |

**⚠️ Multifactor means factors from *different* categories.** Password plus security question is **not** MFA — both are knowledge. Password plus a texted code **is** MFA: knowledge plus possession.

The categories fail independently: stealing a password is remote and scalable, stealing a phone is physical and one at a time.

#### Single sign-on (SSO)

**One authentication event grants access to multiple independent systems.** The user authenticates to an identity provider, which then vouches for them to each application.

**⚠️ SSO is not "the same password everywhere."** That is password synchronisation. Under real SSO the application **never sees the credential** — it receives a signed token or assertion from the identity provider and trusts it.

| | Benefit | Cost |
|---|---|---|
| Users | One credential to remember, so fewer weak and reused passwords | — |
| Administrators | **Central revocation** — disable one account and access ends everywhere | — |
| Security | Fewer credentials in circulation to steal | **Concentration of risk** — compromise one credential and everything falls |

That concentration is why **SSO and MFA are deployed together**. SSO makes one credential extremely valuable; MFA stops that value being realised.

#### AAA — RADIUS vs. TACACS+

| | **RADIUS** | **TACACS+** |
|---|---|---|
| Full name | Remote Authentication Dial-In User Service | Terminal Access Controller Access Control System Plus |
| Transport | **UDP** 1812 (auth), 1813 (accounting) | **TCP** 49 |
| Encrypts | **Password field only** — rest of the packet is cleartext | **The entire payload** |
| AAA separation | Authentication and authorization **combined**; accounting separate | All three **fully separated** |
| Origin | IETF open standard — **cross-vendor** | Cisco-developed, widely implemented |
| Primary use | **Network access** — 802.1X, Wi-Fi, VPN | **Device administration** — which commands an admin may run |

**The purpose split is the thing to memorise.** RADIUS decides *may this user onto the network*. TACACS+ decides *may this administrator type this command on this router*.

That difference explains the design: per-command authorization means a separate authorization exchange for every command typed, so authorization must be independent of authentication — which is exactly what TACACS+ separates and RADIUS does not.

**⚠️ Two facts carry most of the questions:**
- **TACACS+ is TCP, RADIUS is UDP.**
- **RADIUS encrypts only the password.** Username, authorization attributes, and accounting data travel in cleartext, which is why RADIUS traffic is kept on a management network or wrapped in IPsec.

**Accounting** is the third A and the one people forget: recording *what happened* — session start and stop, bytes transferred, commands executed. It is the audit trail that makes the other two provable after the fact.

#### LDAP — Lightweight Directory Access Protocol

**A directory query protocol first, an authentication mechanism second.** It reads and writes a hierarchical database of objects — users, groups, computers.

| | |
|---|---|
| Ports | **TCP 389** plaintext, **TCP 636** for LDAPS |
| Structure | Tree of entries addressed by DN (Distinguished Name), built from CN, OU, DC components |
| How it authenticates | A **bind** operation — supplying credentials the directory validates |

**⚠️ A plain bind on port 389 sends credentials in cleartext.** Use LDAPS on 636, or StartTLS to upgrade a 389 connection.

**⚠️ LDAP is not Active Directory.** AD is Microsoft's directory *service*; LDAP is one protocol for querying it. AD's actual user authentication is done by **Kerberos**.

#### SAML — Security Assertion Markup Language

**XML-based, specifically for web single sign-on and federation.**

| Role | Who |
|---|---|
| **Principal** | The user |
| **Identity provider (IdP)** | Authenticates the user, issues a signed assertion |
| **Service provider (SP)** | The application, which trusts the assertion rather than checking a password |

The point is **federation** — SSO across organisational boundaries. A third-party SaaS application never holds the user's password.

**⚠️ Match the protocol to the access type.** SAML = web application SSO. RADIUS = network access. TACACS+ = device administration. LDAP = directory lookup. Most questions are solvable from that mapping alone.

#### Time-based authentication

Two readings, both used by CompTIA:

1. **TOTP — Time-based One-Time Password.** A code derived from a shared secret plus the current time, valid ~30 seconds. The authenticator-app code; a **possession** factor.
2. **Time-of-day restrictions.** An account permitted to log in only during defined hours.

**⚠️ TOTP depends entirely on clock synchronisation.** Server and token drift apart, valid codes are rejected. The symptom is "MFA suddenly failing for everyone" and the cause is NTP — time services from objective 3.4 are a security dependency, not just operational hygiene.

**Drift direction decides the failure mode.** Server clock **behind** → the server validates against a window already past, so a previously captured code still computes as correct (fail open). Server clock **ahead** → genuine current codes are rejected (fail closed, the common help-desk symptom).

Two things blunt the fail-open case: RFC 6238 says a verifier **should burn accepted codes** and reject reuse within a window, and codes are normally submitted over TLS, so capture comes from phishing or endpoint malware rather than sniffing. Drift matters most because it lengthens the time a **phished** code stays usable.

**Comparison with certificate expiry** — same class of failure, different mechanism:

| | **Certificate** | **TOTP** |
|---|---|---|
| Where the time lives | **Inside the signed object** — notBefore/notAfter | **Nowhere.** The code *is* a function of time |
| Whose clock decides | The **verifier's** | The **server's** |
| Second line of defence | **Revocation** (CRL/OCSP) — not time-based | **Single-use enforcement**, if implemented |

The certificate version of the attack has a name: **clock rollback** — set a device's clock back and expired or revoked certificates validate again. A real problem on embedded and IoT gear with no trusted time source.

**⚠️ Time is a security dependency, not operational hygiene.** Certificates, TOTP, Kerberos tickets, and log correlation all break if time is wrong — and an attacker who controls the time source attacks all of them at once. This is why NTS (Network Time Security) exists.

### Authorization

**Least privilege is the principle. RBAC is a mechanism for implementing it.**

#### Least privilege

Every user, process, and service gets **the minimum access required to do its job, and nothing more**.

**⚠️ It applies to service accounts, not just people.** The most commonly missed part — database services running as domain administrator, backup agents with write access everywhere, monitoring accounts with shell rights.

The reason is **blast radius**, not distrust: what an attacker inherits when they compromise an account. A phished user with read access to one share is an incident; a phished local admin everywhere is a breach.

**Privilege creep** is the slow failure — a person changes roles, gains new access, never loses the old. Countered by **periodic access review or recertification**, which is why audits from objective 3.1 are a control and not paperwork.

- **Separate administrative accounts** — a normal account for email and browsing, a distinct privileged account for administrative work only.
- **Just-in-time access** — privilege granted for a defined window and automatically revoked.

#### Role-based access control (RBAC)

Permissions attach to **roles**; users are assigned roles. Permissions are never granted to individuals directly.

| | Without RBAC | With RBAC |
|---|---|---|
| New hire | Copy another user's permissions and hope | Assign the role; access exactly defined |
| Role change | Old access lingers — privilege creep | Remove old role, add new one |
| "Who can read payroll?" | Enumerate every user | **Read the role** |

The real benefit is that RBAC makes access **reviewable** without inspecting every account.

**⚠️ MAC has two meanings, both in Domain 4.** In access control, **MAC = Mandatory Access Control** — system-enforced labels and clearances the owner cannot override. In objective 4.2, **MAC flooding** means Media Access Control.

| Model | Who decides access |
|---|---|
| **DAC** — Discretionary | The **owner** of the resource |
| **MAC** — Mandatory | The **system**, via labels and clearance |
| **RBAC** — Role-based | The **role assignment** |
| **ABAC** — Attribute-based | **Rules over attributes** — department, device, time, location |

**⚠️ Role explosion** is RBAC's failure mode: so many narrow roles that it becomes per-user permissions with extra steps.

*Homelab: the inter-VLAN firewall policy is least privilege at the network layer — default deny, each permitted flow added deliberately.*

### Geofencing

A **virtual boundary around a physical location**, with access decisions made on whether the device is inside it — the "somewhere you are" factor made concrete. Implemented from GPS, cellular or Wi-Fi positioning, or IP geolocation; accuracy varies enormously between those.

- Block authentication from countries the organisation does not operate in
- Restrict an application to a campus or building
- Trigger an MDM action — lock or wipe — when a device leaves a site

**⚠️ Weak as a sole control.** A VPN relocates an IP address in seconds and GPS can be spoofed. Treat it as a **risk signal**, not a gate — in practice it adds friction (step-up verification) rather than blocking outright.

## Physical security

### Control types

| Type | What it does | Examples |
|---|---|---|
| **Deterrent** | Discourages an attempt | Signage, visible cameras, lighting |
| **Preventive** | Stops the act | **Locks**, doors, access control vestibule, fences |
| **Detective** | Reveals it happened | **Cameras**, logs, alarms, motion sensors |
| **Corrective** | Restores after | Backups, incident response |
| **Compensating** | Substitutes when the primary control is not feasible | Guard posted where a lock cannot be fitted |

### Camera

**Primarily detective — it records, it does not stop anyone.** Visible cameras are also a deterrent. **Never preventive**, and that distinction is the exam point.

Considerations: **coverage** (entrances, racks, and the gaps), **retention period**, lighting and infrared, motion-triggered recording, fixed versus PTZ. Footage is potential evidence — chain of custody applies.

### Locks

**Preventive.**

| Lock | Trade-off |
|---|---|
| **Physical key** | Cheap; no audit trail, keys get copied, rekeying is expensive |
| **Combination / cipher** | No keys to lose; the code spreads and is rarely changed |
| **Electronic badge / proximity** | **Logged and instantly revocable** — what justifies the cost |
| **Biometric** | Hardest to share; cost, false rejects, privacy concerns |

Not only doors: **rack and cabinet locks**, **port locks and blockers** for unused ports, locked enclosures over console connections.

**⚠️ Locks are defeated by people, not tools.** Tailgating bypasses any lock, which is why an **access control vestibule** admits one person at a time. Tailgating appears in objective 4.2.

*Homelab: the console port is unauthenticated at the physical layer — physical access to it is equivalent to administrative access.*

## Deception technologies

| | **Honeypot** | **Honeynet** |
|---|---|---|
| Scale | **One decoy system** | **A network of them** — sometimes a whole simulated segment |
| Shows you | That someone is probing | **Lateral movement** — how an attacker traverses, not just that they arrived |

**The defining property is that it has no legitimate purpose.** Nothing should ever touch it, so *any* interaction is suspicious by definition. That is why it is valuable next to an IDS: an IDS must separate malicious traffic from a flood of legitimate traffic and produces false positives doing it. A honeypot has **no legitimate traffic to confuse it with**.

**⚠️ It is detective, not preventive.** A honeypot stops nothing. It tells you someone is inside, and buys time.

- **Low- vs high-interaction.** Low-interaction *emulates* services — safe, cheap, limited intelligence. High-interaction is a real operating system — rich data, and **a real system an attacker can pivot from**. That risk is why high-interaction honeypots sit in isolated segments.
- **Honeytoken / honeyfile** is data rather than a system — a fake credential, a fake database record, a document nobody should open. Any use of it is proof of compromise. Not in the objectives by name, but it appears as a distractor.

## Common security terminology

| Term | Is |
|---|---|
| **Vulnerability** | A **weakness** — unpatched software, a default password, an open port |
| **Threat** | A **potential cause of harm** — an actor, or an event like a flood |
| **Exploit** | The **means** of taking advantage of a vulnerability |
| **Risk** | The **likelihood and impact** of a threat exercising a vulnerability |

**⚠️ Risk requires both a threat and a vulnerability.** A vulnerability nothing can reach carries low risk; a threat with no corresponding weakness carries low risk. Questions are built on exactly that — describing one in isolation and asking for the risk.

**⚠️ The exploit is not the vulnerability.** The weakness is the unpatched service; the exploit is the code that abuses it.

**Risk responses** — accept, avoid, mitigate, transfer. **⚠️ Transfer moves impact, never accountability.** Insurance or outsourcing pays for the breach; the regulator and the customers still come to you.

### A mnemonic for the four

| | |
|---|---|
| **Vulnerability** | **WHAT** is weak |
| **Threat** | **WHAT COULD** cause harm — actor *or* event |
| **Threat actor** | **WHO** |
| **Exploit** | **HOW** |
| **Risk** | **SO WHAT** — likelihood x impact |

**⚠️ Threat is not always a who.** Fire, flood, power failure and hardware death are threats with no actor, and CompTIA uses environmental threats in questions precisely because people collapse "threat" into "attacker." The **threat actor** is the who; the threat is the broader category.

Two more that slot in: **threat vector** is *through what* — the path in, such as email, USB, or an exposed port — and **attack surface** is every vector added together.

**Worked example:**

- **Vulnerability** — a server concatenates unsanitised input into a query
- **Exploit** — the crafted input abusing it: `' OR 1=1--`
- **Attack** — the act of sending it
- **Threat actor** — whoever sent it
- **Risk** — likelihood x what is in the database

**⚠️ "SQL injection" is used for the vulnerability class, the technique, and the payload interchangeably.** Normal usage, but exam options separate them — read which one the question wants.

### CIA triad

| Leg | Controls that serve it |
|---|---|
| **Confidentiality** | Encryption, access control, MFA |
| **Integrity** | **Hashing**, digital signatures, checksums |
| **Availability** | Redundancy, backups, load balancing, DDoS protection |

**⚠️ Hashing is integrity, not confidentiality.** The most-tested mismatch in this section. A hash proves data has not changed; it is not there to hide it.

**⚠️ The legs pull against each other.** Replicating data across sites improves availability and increases confidentiality exposure — more copies, more places to steal it from. Questions asking for "the trade-off" want that.

## Audits and regulatory compliance

### Data locality

Where data physically resides, and therefore whose laws govern it. Cloud makes this a live problem, because "the cloud" has a physical address and a **region setting is the control**.

Three words that get conflated: **residency** is where it is stored, **sovereignty** is whose law applies, **locality** is the general requirement that these be deliberate.

### PCI DSS — Payment Card Industry Data Security Standard

**⚠️ It is not a law.** It is a contractual standard imposed by the card brands. Breaching it costs fines and the ability to process cards, not prosecution.

**⚠️ Why it appears in a networking exam: segmentation reduces scope.** Every system touching cardholder data is in the CDE (Cardholder Data Environment) and must be audited. Isolating that environment shrinks what is assessed — turning VLANs and firewall rules into a direct cost saving, and making this the most likely PCI question on the exam.

### GDPR — General Data Protection Regulation

**⚠️ It is extraterritorial.** It follows **EU residents' data**, not EU companies — a Canadian business with EU customers is in scope.

Key facts: **72-hour breach notification**, rights to access, erasure and portability, and fines up to **4% of global annual turnover**.

**⚠️ Compliance is not security.** A compliant organisation has met a minimum defined by someone who has never seen its network. Passing an audit and being defensible are different claims.

## Network segmentation enforcement

**The thesis behind grouping these four:** each is a case where **the endpoint cannot be trusted or fixed**, so the network has to be the control. Every question here reduces to that.

### IoT and IIoT

**IoT** is consumer and commercial — cameras, thermostats, smart plugs, TVs. **IIoT** is sensors and actuators in manufacturing and energy.

| Problem | Consequence |
|---|---|
| **Rarely patched**, often never | Known vulnerabilities stay open for the device's life |
| **Default or hardcoded credentials** | Mirai built a botnet from exactly this |
| **10-15 year lifespans** | The vendor stops shipping updates long before retirement |
| **Cloud dependencies** | It phones home to infrastructure you do not control |

**⚠️ The control is segmentation, not hardening — because hardening is not available.** You cannot install an agent on a smart plug. You can decide it reaches the internet and nothing else.

### SCADA, ICS, and OT

| Term | Is |
|---|---|
| **OT** — Operational Technology | The **broad category**: technology interacting with the physical world |
| **ICS** — Industrial Control Systems | The systems **controlling physical processes** |
| **SCADA** — Supervisory Control and Data Acquisition | The layer that **monitors and supervises** ICS, often across wide geography |

**⚠️ The CIA triad inverts here** — availability and safety first, confidentiality last. A stolen sensor reading is an inconvenience; a stopped turbine or an unsafe valve state can kill someone. **"Patch it immediately" is frequently the wrong answer in an OT scenario.**

**⚠️ OT protocols have no security by design.** Modbus, DNP3 and Profinet predate the assumption that networks are hostile — no encryption, no authentication. Isolation *was* the security model.

**⚠️ "Air gapped" is the classic control and the classic myth.** Stuxnet crossed one via USB. Modern practice is the **Purdue model** — layered zones with a DMZ between IT and OT — rather than a claimed gap nobody can verify.

### Guest

Internet only, no path to internal resources: **separate VLAN and SSID**, **client isolation**, captive portal, bandwidth limits.

**⚠️ Client isolation is the one that gets forgotten**, and it is the difference between a guest network and a free hostile LAN — without it, one compromised laptop in the lobby can attack every other guest.

**⚠️ A "guest network" sharing a VLAN with anything internal is not a guest network**, whatever the SSID is called.

### BYOD

**The core problem is ownership, not technology.** You do not control patch level, apps, or who else uses the device.

| Control | Does |
|---|---|
| **MDM** — Mobile Device Management | Enforces policy, enables remote wipe |
| **NAC** — Network Access Control | **Posture checks** — admits the device only if it meets a standard |
| **Containerisation** / work profile | Separates corporate from personal data on one device |
| **Dedicated VLAN** | The fallback when the above cannot be enforced |

**⚠️ The tension is privacy against control, and it is legal rather than technical.** Remote-wiping a personal phone destroys someone's photos — an HR problem before a security one. Containerisation exists so you can wipe the container and leave the phone.

**⚠️ Know the alternatives as distractors:** **COPE** (Corporate-Owned, Personally Enabled), **CYOD** (Choose Your Own Device), and corporate-owned business-only. They trade cost against control; BYOD is the cheapest and least controlled.
