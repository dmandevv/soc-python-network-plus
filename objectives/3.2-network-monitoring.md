# 3.2 — Given a scenario, use network monitoring technologies

## Methods

### SNMP
**Simple Network Management Protocol** — the standard mechanism for querying and managing network devices remotely.

**Three components:**

| Component | Role |
|---|---|
| **Managed device** | The equipment being monitored — switch, router, server |
| **Agent** | Software running **on** that device, exposing its data |
| **NMS (network management system)** | The collector that queries agents and stores results |

**⚠️ Two ports, running in opposite directions:**

| Port | Listener | Direction |
|---|---|---|
| **UDP 161** | The **agent** | Manager → device (**polling**) |
| **UDP 162** | The **manager** | Device → manager (**traps**) |

**This distinction matters for firewall rules.** Permitting 161 enables polling and does nothing for traps, which arrive on 162 in the opposite direction — configure one and omit the other and half the monitoring silently fails.

**Operations:**

| Operation | Purpose |
|---|---|
| **GET** | Read a single value |
| **GETNEXT** / **GETBULK** | Walk multiple values; GETBULK was added in v2c |
| **SET** | **Write** — modify a setting on the device |
| **TRAP** / **INFORM** | Alert initiated by the device |

**⚠️ SNMP is a management protocol, not only a monitoring one.** The **SET** operation writes, so a credential with write access can reconfigure equipment — shut down interfaces, alter settings, change routing. This is what makes the community-string weakness in v1 and v2c a genuine risk rather than a theoretical one.

**The polling model:** the manager queries on a schedule, commonly every 30 or 60 seconds. Load is predictable and devices transmit nothing until asked, but **detection is delayed by up to one polling interval** — a failure occurring immediately after a poll is not observed until the next one. That gap is why traps exist.

## Solutions

### Network discovery
Determining **what is actually present on the network**, as distinct from what the records claim. It is how the asset inventory of objective 3.1 is populated and kept honest, since manual records never contain equipment nobody reported.

| | **Active** | **Passive** |
|---|---|---|
| Method | Sends probes — ping sweeps, ARP scans, port scans | Observes existing traffic — flow data, mirrored traffic |
| Speed | Fast and thorough | Accumulates over time |
| Finds | Anything that responds | **Only devices that transmit** |
| Detectable | Yes, and potentially disruptive | **Invisible** |

**ARP scanning is more reliable than ICMP on a local segment** — many hosts drop pings, but nothing can operate without answering ARP.

| | **Ad hoc** | **Scheduled** |
|---|---|---|
| Timing | On demand | Recurring |
| Answers | "What is on this subnet now?" | **"What changed since the last scan?"** |

**⚠️ The value of scheduled discovery is the difference between scans, not the scan itself.** A new device, a newly opened port, or a host that has disappeared are all detections — and only a history of previous scans makes them visible.

**⚠️ Active scanning can disable fragile equipment.** Older printers, industrial and operational technology, building management systems, and medical devices frequently have network stacks that were never hardened against unexpected input. It also generates alerts in the organisation's own IDS, which it should.

**Documented, predictable scanning is worth more than ad hoc scanning** for a further reason: an attacker's reconnaissance and a legitimate scan look nearly identical, and knowing the schedule is what distinguishes them.

### Traffic analysis
Interpreting collected traffic data. **The methods above gather; traffic analysis is what the data is used for**, and the same dataset answers operational and security questions.

**Operationally:** top talkers, protocol distribution, temporal patterns, and capacity planning — knowing a link has grown steadily for months indicates when to upgrade it before users report a problem.

**For security:** regular intervals to a single destination indicate **beaconing**; large outbound volume at unusual hours indicates **exfiltration**; a host suddenly contacting many internal hosts indicates **lateral movement**; abnormal DNS volume indicates **tunnelling**.

**⚠️ Lateral movement is east-west traffic by definition** (objective 1.6). An attacker already inside the network does not cross the perimeter again, so a monitoring strategy that watches only the edge cannot see it. **Internal segmentation therefore aids visibility as well as containment** — VLAN boundaries force internal traffic through the router, which is the only point at which it can be observed.

**Encryption limits content analysis but not pattern analysis.** Timing, volume, direction, and endpoints all survive TLS, and those are the properties beaconing and exfiltration are recognised by — which is why flow data has grown more valuable as packet capture has grown less so.

**Traffic analysis depends entirely on baseline metrics**, since "unusual" has no meaning without a record of usual.

### Performance, availability, and configuration monitoring

| | Asks | Answer type |
|---|---|---|
| **Availability** | **Is it up?** | Binary |
| **Performance** | **Is it working well?** | Quantitative |
| **Configuration** | **Has it changed?** | A difference |

**Availability monitoring** tests reachability by ICMP, TCP port check, HTTP request, or SNMP, and produces the **uptime percentage** that SLA "nines" express.

**⚠️ Responding to ICMP is not the same as working.** A host can answer pings while its application is dead or returning errors to every request. **Service-level checks that validate a response are materially better than host-level reachability checks**, and the gap between them is where most falsely reassuring dashboards originate.

**Performance monitoring** measures bandwidth utilisation, latency, jitter, packet loss, CPU, memory, disk I/O, and response time against the baseline.

**⚠️ It catches degradation without failure**, which availability monitoring cannot. A service responding in thirty seconds passes every availability check while being unusable — **availability monitoring alone will report 100% uptime throughout a severe outage.**

**Configuration monitoring** detects drift from the configuration baseline, either by periodically pulling configurations and comparing them against a known-good copy, or by alerting on logged change events.

**⚠️ An unexpected difference is either an undocumented change or an intrusion**, and the two are indistinguishable from the difference alone — which makes configuration monitoring a detection capability rather than an administrative one.

**All three are required because each detects a failure the others cannot see:** a crashed server (availability), a server responding far too slowly (performance), and a firewall rule that appeared overnight with no change record (configuration).
