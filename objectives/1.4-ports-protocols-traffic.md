# 1.4 — Explain common networking ports, protocols, services, and traffic types

## Protocols and ports

### File Transfer Protocol (FTP) — 20/21 (TCP)
Transfers files between a client and server using **two separate connections**: port **21** carries commands (the control channel) and port **20** carries the file data. It transmits everything — including credentials — in **cleartext**, so it has been superseded by SFTP (port 22) and FTPS for anything security-sensitive.

**Active vs. passive mode:** in *active* mode the server initiates the data connection back to the client from port 20, which client-side firewalls and NAT typically block. In *passive* mode the server supplies a port for the client to connect to, so the client initiates both connections — which is why passive is the default in practice.

### Secure File Transfer Protocol (SFTP) — 22 (TCP)
A file transfer protocol that runs **inside an SSH session**, inheriting SSH's encryption and authentication and using SSH's port 22. Despite the name it shares no code or design with FTP — it uses a **single connection** for both commands and data, which makes it firewall- and NAT-friendly with no active/passive complication.

**SFTP vs. FTPS:** SFTP is SSH-based on one port (22); **FTPS** is the original FTP wrapped in TLS, keeping FTP's two-connection design and its firewall difficulties.

### Secure Shell (SSH) — 22 (TCP)
Provides **encrypted remote command-line access** to a device, replacing Telnet's cleartext equivalent. Beyond a shell, it also carries other protocols — SFTP, SCP, port forwarding, and tunnels — which is why port 22 serves several functions at once.

**Key features:** public-key authentication (stronger than passwords), host-key verification so the client detects an impersonated server, and the ability to tunnel arbitrary TCP traffic through the encrypted session.

### Telnet — 23 (TCP)
Provides remote command-line access in **cleartext**, with no encryption of any kind — credentials and every keystroke are readable by anyone capturing the traffic. It has been superseded by SSH for all remote administration, and surviving instances are treated as a finding to remediate rather than a protocol to configure.

**Where it still appears:** legacy equipment, out-of-band console servers, and as a quick connectivity test (`telnet host 443`) to check whether a TCP port is open — that last use is legitimate and common.

### Simple Mail Transfer Protocol (SMTP) — 25 (TCP)
The protocol for **sending** and relaying email between mail servers. It is send-only — retrieving mail from a mailbox uses POP3 or IMAP instead, which is the distinction most commonly tested.

**Ports:** 25 is the traditional server-to-server relay port and is widely blocked outbound by ISPs to limit spam; **587** (SMTPS/submission) is the port clients use to submit mail with authentication and STARTTLS encryption.

### Domain Name System (DNS) — 53 (UDP and TCP)
Resolves human-readable names to IP addresses, distributed hierarchically across root servers, TLD registries, and authoritative nameservers. It is the only protocol in this list that routinely uses **both UDP and TCP on the same port**: UDP 53 for ordinary queries (fast, low overhead), TCP 53 for zone transfers and any response too large for a single UDP datagram.

### Dynamic Host Configuration Protocol (DHCP) — 67/68 (UDP)
Automatically assigns IP addresses, subnet masks, default gateways, and DNS servers to clients. The **server listens on UDP 67** and the **client on UDP 68**; the exchange follows the **DORA** sequence — Discover, Offer, Request, Acknowledge.

**Why it uses broadcast:** a client has no IP address yet, so it cannot send a unicast packet. Discover and Request are broadcast, which is also why they do not cross routers without a **relay agent / IP helper** forwarding them as unicast to a server on another subnet.

### Trivial File Transfer Protocol (TFTP) — 69 (UDP)
A deliberately minimal file transfer protocol with **no authentication, no encryption, and no directory browsing** — a client can only get or put a file whose exact name it already knows. It runs over **UDP**, unlike FTP and SFTP, and implements its own simple acknowledgement scheme.

**Where it is used:** network device configuration backups and firmware loading, and **PXE network booting**, where the tiny code footprint matters because it must fit in firmware before an OS exists. Its lack of security confines it to trusted management networks.

### Hypertext Transfer Protocol (HTTP) — 80 (TCP)
The request/response protocol carrying web traffic, transmitted in **cleartext** — readable and modifiable by anyone on the path. It is **stateless**, meaning the server retains no memory between requests, which is why cookies and sessions exist to layer state on top.

**Status quo:** superseded by HTTPS (443) for essentially all traffic; port 80 today usually exists only to redirect visitors to the encrypted version.

### Network Time Protocol (NTP) — 123 (UDP)
Synchronizes clocks across networked devices, organized in a hierarchy of **stratum** levels — stratum 0 is a reference clock (GPS, atomic), stratum 1 servers attach directly to one, and each level below adds a hop.

**Why accurate time matters:** log correlation across systems is impossible without it, Kerberos authentication rejects requests with excessive clock skew, and TLS certificate validity checks depend on the current time being correct. Clock drift therefore produces authentication and certificate failures that look unrelated to time.

### Simple Network Management Protocol (SNMP) — 161/162 (UDP)
Monitors and manages network devices by polling them for status information. **Port 161** is where the *agent* on the managed device listens for queries; **port 162** is where the *manager* listens for **traps** — unsolicited alerts a device sends when something happens, rather than waiting to be asked.

**Versions matter for security:** v1 and v2c authenticate only with a cleartext **community string** (commonly left at the default `public`), while **v3** adds real authentication and encryption and is the only version acceptable on an untrusted network.

**On the version numbering:** the original SNMPv2's security model was too complex to be adopted, so **v2c** ("c" for community) shipped v2's functional improvements — bulk retrieval, better error handling — while reverting to v1's cleartext community strings. Its security is therefore identical to v1, which is why the meaningful jump is to v3.

### Lightweight Directory Access Protocol (LDAP) — 389 (TCP)
Queries and modifies a **directory service** — the hierarchical database holding users, groups, computers, and their attributes. It is the protocol behind centralized authentication and identity lookups, most visibly in Microsoft Active Directory.

**Security:** plain LDAP on 389 transmits queries and **bind credentials in cleartext**. **LDAPS** (port 636) wraps the session in TLS, and StartTLS can upgrade a 389 connection in place.

**Implicit vs. explicit TLS** — a pattern running through this whole port list. *Implicit* means a dedicated always-encrypted port (443, 636, 465, 993, 995); *explicit* (**STARTTLS**) means connecting to the normal port in cleartext and upgrading in place (SMTP 25/587, IMAP 143, POP3 110, LDAP 389). STARTTLS is vulnerable to **stripping** — an on-path attacker removes the server's advertisement of TLS support so the client silently stays in cleartext — which implicit-TLS ports cannot suffer.

### Hypertext Transfer Protocol Secure (HTTPS) — 443 (TCP)
HTTP carried inside a **TLS** session, providing confidentiality, integrity, and server authentication via certificates. It is now the default for essentially all web traffic, with port 80 relegated to issuing redirects.

**What the certificate provides:** proof the server is who it claims to be, validated against a trusted **certificate authority** — which is what prevents an attacker from simply presenting their own encrypted connection instead.

### Server Message Block (SMB) — 445 (TCP)
The Windows protocol for **file and printer sharing**, and the mechanism behind mapped network drives and UNC paths (`\\server\share`). It is the file-level protocol a Windows-oriented NAS serves, alongside NFS on the Unix side.

**Security note:** SMB should never be exposed to the internet — port 445 is the vector WannaCry and NotPetya used via the EternalBlue exploit, and it remains one of the most heavily scanned ports. SMBv1 is deprecated and should be disabled outright.

### Syslog — 514 (UDP; TCP also used)
The standard protocol for shipping **log messages** from devices to a central collector, so events from firewalls, switches, servers, and applications land in one searchable place. Each message carries a **facility** (what generated it) and a **severity** level from 0 (emergency) to 7 (debug).

**Transport caveat:** traditional syslog uses **UDP 514**, which is fire-and-forget — messages can be lost silently with no retransmission. TCP 514 and TLS-protected syslog (6514) address reliability and confidentiality, which matters when logs are evidence.

### Simple Mail Transfer Protocol Secure (SMTPS) — 587 (TCP)
The **mail submission** port, where authenticated clients hand outgoing messages to their own mail server, secured with **STARTTLS**. It exists to separate client submission from the server-to-server relay traffic on port 25, so that submission can require authentication while relay does not.

**Port note:** 587 is submission with explicit TLS (STARTTLS). Port **465** is the older implicit-TLS submission port, still widely supported. The objectives list 587 as SMTPS.

### Lightweight Directory Access Protocol over SSL (LDAPS) — 636 (TCP)
LDAP wrapped in **implicit TLS** — encrypted from the first byte on a dedicated port, rather than upgrading in place. It protects the directory queries and, critically, the **bind credentials** that plain LDAP on 389 sends in cleartext.

**Why it matters more than most encrypted variants:** an LDAP bind carries working domain credentials, so capturing plaintext LDAP traffic yields directly usable account access with no cracking required.

**SSL vs. TLS:** SSL is the deprecated predecessor — all versions (2.0, 3.0) are broken and disabled, as are TLS 1.0 and 1.1 since 2021. **TLS 1.2 is the practical floor, 1.3 the target.** The word "SSL" survives only in product naming ("SSL certificate", "LDAP over SSL"), where it invariably means TLS.

### Structured Query Language (SQL) Server — 1433 (TCP)
The default port for **Microsoft SQL Server**, over which clients send queries and receive result sets. It should be reachable only from application servers on an internal segment — never exposed to the internet, where it is continuously scanned and brute-forced.

**Other databases for contrast (not on the exam list):** MySQL/MariaDB 3306, PostgreSQL 5432, Oracle 1521, MongoDB 27017.

### Remote Desktop Protocol (RDP) — 3389 (TCP)
Microsoft's protocol for **graphical remote access** to a Windows desktop — the GUI counterpart to SSH's command line. It transmits screen updates to the client and keyboard/mouse input back to the host.

**Security:** RDP exposed to the internet is one of the most exploited entry points in existence, being the primary initial-access vector for ransomware campaigns via credential stuffing and brute force. It belongs behind a VPN or a jump box, never directly published.

### Session Initiation Protocol (SIP) — 5060/5061 (TCP and UDP)
The signalling protocol that **establishes, modifies, and terminates** voice and video calls — it sets up the session but carries no audio itself. The media stream travels separately over **RTP** on dynamically negotiated ports, which is why SIP is a Layer 5 (session) protocol rather than a media one.

**Ports:** **5060** is unencrypted signalling; **5061** is SIP over TLS (SIPS). Encrypting signalling does not encrypt the call — that requires **SRTP** for the media stream.

## Internet Protocol (IP) types

### Internet Control Message Protocol (ICMP)
The **diagnostic and error-reporting** protocol of the IP suite. It carries no application data and uses **no ports** — it rides directly on IP as protocol number 1, which is why firewall rules for it specify message *types* rather than port numbers.

**What depends on it:** `ping` (echo request/reply, types 8 and 0), `traceroute` (time exceeded, type 11), and **Path MTU Discovery** (destination unreachable / fragmentation needed, type 3). Blocking ICMP wholesale therefore breaks PMTUD and traceroute — types 3 and 11 must be permitted even in restrictive environments.

### Transmission Control Protocol (TCP)
The **connection-oriented, reliable** transport protocol. It establishes a session via the **three-way handshake** (SYN → SYN-ACK → ACK), numbers every byte so data can be reassembled in order, acknowledges receipt, and retransmits anything lost. It also provides **flow control** (a receiver-advertised window, so a fast sender cannot overwhelm a slow receiver) and **congestion control** (backing off when the network is saturated).

**Cost of those guarantees:** handshake latency before any data moves, larger headers, and head-of-line blocking — one lost segment stalls delivery of everything behind it. Used where correctness matters more than latency: web, email, file transfer, SSH, databases.

### User Datagram Protocol (UDP)
The **connectionless, best-effort** transport protocol. It adds little beyond source and destination ports and a checksum, then sends — no handshake, no acknowledgements, no retransmission, no ordering, no congestion control. Its 8-byte header is less than half TCP's minimum 20.

**Why that is a feature:** for real-time media a retransmitted packet arrives too late to be useful, so recovery would add delay without benefit. Used by DNS, DHCP, TFTP, NTP, SNMP, syslog, and RTP voice/video.

| | TCP | UDP |
|---|---|---|
| Connection | Handshake first | **Connectionless** |
| Reliability | Guaranteed, retransmits | **Best effort** |
| Ordering | Sequenced | None |
| Flow/congestion control | Yes | **No** |
| Header | 20 bytes min | **8 bytes** |
| Suits | Web, email, file transfer, SSH | DNS, DHCP, NTP, voice, video |

**Security consequence of connectionlessness:** UDP source addresses are trivially spoofed, since no handshake verifies the sender. This is the basis of **amplification DDoS** — a small spoofed request producing a large reply aimed at the forged address. DNS, NTP, and SNMP have all been abused this way.

### Generic Routing Encapsulation (GRE)
A **tunneling protocol** (IP protocol 47) that wraps arbitrary Layer 3 payloads inside an IP packet, creating a virtual point-to-point link across an intervening network. It provides **no encryption and no authentication** — purely encapsulation.

**Why it exists:** unlike a plain IP path, a GRE tunnel can carry traffic IP alone will not, notably **multicast and routing protocol updates**, which is what lets dynamic routing run across the tunnel. Because it offers no security, it is commonly paired as **GRE over IPsec** — GRE supplies the flexible tunnel, IPsec supplies confidentiality.

### Internet Protocol Security (IPsec)
A **suite** of protocols securing traffic at Layer 3, so every protocol above it is protected without any application awareness. It is the standard basis for site-to-site VPNs.

**Two modes:** **transport mode** encrypts only the payload, leaving the original IP header exposed (host-to-host on a trusted network); **tunnel mode** encapsulates the *entire* original packet inside a new one, hiding the internal addressing — which is what site-to-site VPNs use.

**Three components**, each covered separately below: **AH** (integrity and authentication, no encryption), **ESP** (encryption plus integrity), and **IKE** (negotiates keys and establishes the security association).

#### Authentication Header (AH)
Provides **integrity and origin authentication but no encryption** — the payload travels in cleartext, verifiably unaltered and verifiably from the claimed sender. IP protocol 51.

**Its distinguishing property:** AH authenticates the **outer IP header** as well as the payload, which is stronger tamper protection than ESP offers — but that same coverage means **AH breaks through NAT**, because NAT rewrites header fields AH is protecting. This is why AH is rarely deployed today; virtually all real IPsec uses ESP.

#### Encapsulating Security Payload (ESP)
Provides **encryption, integrity, and authentication** — the component that actually makes IPsec confidential. IP protocol 50. It protects the payload and its own header but **not the outer IP header**, which is precisely why it survives NAT where AH cannot.

**In tunnel mode** ESP encrypts the entire original packet, hiding internal addressing; an observer sees only gateway-to-gateway traffic. Where NAT sits in the path, **NAT-Traversal** wraps ESP inside UDP 4500 so translation devices can handle it. ESP is what essentially every production IPsec VPN uses.

| | AH | ESP |
|---|---|---|
| Integrity / authentication | ✅ | ✅ |
| **Encryption** | ❌ | ✅ |
| Protects outer IP header | ✅ | ❌ |
| **NAT compatible** | ❌ | ✅ |
| Protocol number | 51 | 50 |

#### Internet Key Exchange (IKE)
Negotiates the **security association (SA)** — the agreed encryption algorithms, authentication method, and keys — before AH or ESP carry any data. It runs over **UDP 500** (and UDP 4500 when NAT-Traversal is in use), and it is the only part of IPsec that uses a port.

**Two phases:** *Phase 1* authenticates the two peers and builds a secure channel for the negotiation itself; *Phase 2* uses that channel to establish the SAs that actually protect user traffic. **IKEv2** is the current version — simpler, faster, with built-in NAT-T and connection resilience.

**Why it matters operationally:** mismatched Phase 1 or Phase 2 proposals between two peers are the most common cause of a site-to-site VPN that will not establish.

**IPsec firewall rules therefore need:** UDP 500 (IKE), UDP 4500 (NAT-T), and IP protocol 50 (ESP).

## Traffic types

### Unicast
**One-to-one** — a single sender to a single, specifically addressed recipient. It is the default for essentially all traffic: web requests, email, SSH, file transfers.

**Scaling property:** the sender transmits a separate copy per recipient. Sending the same video stream to 100 clients means 100 independent streams, which is why unicast is the wrong choice for large-scale simultaneous distribution.

### Multicast
**One-to-many, but only to interested recipients.** The sender transmits a single stream to a multicast group address; the network replicates it only where delivery paths diverge, so no link ever carries a duplicate copy.

**Addressing:** IPv4 multicast is the **Class D** range **224.0.0.0/4** (224–239 in the first octet); IPv6 uses **FF00::/8**. Hosts join and leave groups using **IGMP** (Internet Group Management Protocol), and switches use **IGMP snooping** to forward multicast only out ports with interested listeners rather than flooding it.

**Used by:** IPTV and streaming video distribution, market data feeds, and routing protocols — OSPF (224.0.0.5/.6) and EIGRP (224.0.0.10) send updates to multicast groups rather than broadcasting.

### Anycast
**One-to-nearest.** The *same* IP address is advertised from many geographically separate locations, and routing delivers each request to whichever instance is closest by network path. One address, many servers, no client-side logic.

**Used by:** the DNS root servers (which is how 13 root server addresses are served by hundreds of physical machines worldwide), public resolvers like 8.8.8.8 and 1.1.1.1, and CDN edge networks.

**Why it matters:** it provides low latency and DDoS resilience simultaneously — attack traffic is absorbed by whichever region originates it rather than converging on a single target, and a failed site simply stops being advertised so traffic reroutes automatically.

### Broadcast
**One-to-all** — delivered to every host on the local segment, whether or not it wants the traffic. The IPv4 limited broadcast address is **255.255.255.255**; each subnet also has a directed broadcast (its last address, e.g. 192.168.1.255 for a /24). At Layer 2 the destination MAC is **FF:FF:FF:FF:FF:FF**.

**Scope:** broadcasts do not cross routers — a broadcast domain ends at every router interface, which is the defining property separating switches from routers.

**Used by:** ARP and DHCP Discover, both of which must reach an unknown recipient. **IPv6 removes broadcast entirely**, replacing it with multicast to specific groups so uninterested hosts are never interrupted.

| Type | Recipients | IPv4 addressing |
|---|---|---|
| **Unicast** | One specific host | Ordinary host address |
| **Multicast** | Interested subscribers | 224.0.0.0/4 |
| **Anycast** | Nearest of many instances | Ordinary address, advertised from many sites |
| **Broadcast** | Every host on the segment | 255.255.255.255 or subnet's last address |
