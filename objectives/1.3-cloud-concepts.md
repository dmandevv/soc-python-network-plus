# 1.3 — Summarize cloud concepts and connectivity options

### Network functions virtualization (NFV)
Replaces dedicated networking hardware — routers, firewalls, load balancers — with the same functions running as **software on general-purpose servers**. This decouples the network function from purpose-built hardware, so capacity can be provisioned, scaled, and torn down in minutes instead of purchase cycles.

### Virtual private cloud (VPC)
A logically isolated section of a public cloud provider's infrastructure, dedicated to one customer, within which they define their own IP address range, subnets, route tables, and gateways. It provides the isolation of a private network while running on shared physical hardware — the cloud equivalent of having your own data center network.

**Relation to service models:** a VPC is the network *inside which* IaaS resources live. Under PaaS the provider owns the network but may let services integrate into your VPC; under SaaS there is no VPC to configure at all.

### Network security groups
**Stateful** virtual firewalls applied at the **instance/interface level**, controlling inbound and outbound traffic for the specific resources they are attached to. Because they are stateful, allowing a connection outbound automatically permits its return traffic, and they typically support **allow rules only** — anything not explicitly permitted is denied by default.

### Network security lists
**Stateless** access control lists applied at the **subnet level**, filtering all traffic entering or leaving that subnet regardless of which resources sit inside it. Because they are stateless, inbound and outbound rules must both be written explicitly, and they support **both allow and deny rules**, evaluated in numbered order.

| | Network security group | Network security list |
|---|---|---|
| Scope | Instance / interface | **Subnet** |
| State | **Stateful** | **Stateless** |
| Rule types | Allow only | Allow **and** deny |
| Evaluation | Order-independent | **In rule-number order** |
| Return traffic | Automatic | Must be permitted explicitly |

**Stateless rules and ephemeral ports.** Direction is relative to the instance (inbound = arriving, outbound = leaving); the destination port is a separate axis. Ephemeral ports (~1024–65535) appear on whichever direction carries the *reply*, which flips depending on who initiated:

| Instance role | Direction | Dst port | Rule needed |
|---|---|---|---|
| **Server** (hosts a service) | Inbound (client→server) | 443 | allow dst 443 |
| | Outbound (server→client) | **ephemeral** | allow dst ephemeral |
| **Client** (calls a service) | Outbound (instance→remote) | 443 | allow dst 443 |
| | Inbound (remote→instance) | **ephemeral** | allow dst ephemeral |

Stateful controls (security groups) need only the first rule in each pair.

## Cloud gateways

### Internet gateway
A horizontally scaled, highly available VPC component that provides **bidirectional** internet connectivity for resources holding public IP addresses. Attaching one and adding a route to `0.0.0.0/0` is what turns a subnet into a **public subnet** — resources behind it can both initiate outbound connections and receive unsolicited inbound ones.

### Network address translation (NAT) gateway
A managed service that lets resources in a **private subnet** initiate **outbound-only** connections to the internet, translating their private addresses to the gateway's public one. Return traffic for those connections is permitted, but nothing on the internet can initiate a connection inward — which is what makes it the standard way to let private workloads fetch updates without exposing them.

| | Internet gateway | NAT gateway |
|---|---|---|
| Direction | **Bidirectional** | **Outbound only** |
| Subnet type | Public | Serves **private** subnets |
| Instance needs public IP | Yes | No |
| Inbound connections | Permitted | Blocked |

## Cloud connectivity options

### VPN (to the cloud)
An encrypted tunnel from an on-premises network to a cloud VPC, carried **over the public internet**. It is fast to deploy and inexpensive because it needs no new physical circuit, but inherits the internet's variable latency and offers no bandwidth guarantee — making it the default choice for small or non-critical workloads.

### Direct Connect
A **dedicated private circuit** between an organization's network and the cloud provider, bypassing the public internet entirely. It delivers consistent low latency, guaranteed bandwidth, and an SLA, at the cost of weeks-to-months provisioning time and significant expense — and it is **not encrypted by default**, since privacy comes from the circuit's isolation rather than cryptography.

| | VPN | Direct Connect |
|---|---|---|
| Path | Public internet | **Dedicated private circuit** |
| Provisioning | Hours | **Weeks to months** |
| Cost | Low | High |
| Latency | Variable | **Consistent** |
| Bandwidth | Best effort | **Guaranteed, with SLA** |
| Encryption | Built in (IPsec) | **None by default** |

## Deployment models

### Public cloud
Infrastructure owned and operated by a third-party provider (AWS, Azure, Google Cloud) and shared among many customers over the internet, with resources rented on demand. It offers effectively unlimited scale and no capital expenditure, in exchange for multitenancy and reduced control over where and how data is hosted.

### Private cloud
Cloud infrastructure dedicated to a **single organization** — whether hosted on-premises or by a third party — providing full control over hardware, data location, and security posture. It trades the public cloud's elasticity and zero capital cost for that control, since capacity is bounded by hardware the organization has actually bought.

**Note:** private cloud is not simply "servers you own." It requires cloud characteristics — self-service provisioning, pooled resources, automation, and metered usage — typically via a platform like OpenStack, VMware, or Proxmox. Virtualized servers without that self-service layer are just virtualization.

### Hybrid cloud
A deliberate combination of public and private cloud (or on-premises) infrastructure, connected so that workloads and data can move between them. It lets an organization keep sensitive or steady workloads private while using public cloud for elasticity, at the cost of managing two environments and the connectivity between them.

**Cloud bursting** is the classic pattern: run normal load on private infrastructure and overflow into public cloud only during demand spikes, paying for extra capacity solely when it is used.

## Service models

### Software as a service (SaaS)
Finished application software delivered over the internet, where the provider manages the **entire stack** — infrastructure, platform, and the application itself. The customer only manages their own data and user access, making it the least flexible but lowest-maintenance model.

### Infrastructure as a service (IaaS)
Raw virtualized computing resources — virtual machines, storage, and networking — rented on demand, with the customer managing everything from the **operating system upward**. It is the most flexible and most work-intensive model, and the one where VPCs, subnets, and security groups are yours to design.

### Platform as a service (PaaS)
A managed environment for **running code**, where the provider handles the operating system, runtime, and middleware, and the customer supplies only the application and its data. It removes infrastructure maintenance entirely while keeping application-level control, at the cost of being constrained to the runtimes and versions the platform supports.

**The progression:** IaaS = you get a server. PaaS = you get a place to run code. SaaS = you get an application. Each step hands more of the stack to the provider.

| Layer | IaaS | PaaS | SaaS |
|---|---|---|---|
| Application | You | You | Provider |
| Data | You | You | You |
| Runtime / middleware | You | Provider | Provider |
| Operating system | You | Provider | Provider |
| Virtualization, servers, network | Provider | Provider | Provider |

**Data is yours in all three models** — which is why data protection and access control remain the customer's responsibility regardless of service model.

### Scalability
The ability of a system to **handle growth** by adding resources. **Vertical scaling (scaling up)** makes an existing instance bigger — more CPU or RAM — and is simple but bounded by the largest machine available. **Horizontal scaling (scaling out)** adds more instances behind a load balancer, which has no practical ceiling but requires the application to support running as multiple copies.

### Elasticity
The ability to **automatically** add *and remove* resources in response to real-time demand, without human intervention. Where scalability is the *capacity* to grow, elasticity is growing and shrinking on its own — and the shrinking half is what turns cloud consumption billing into actual cost savings.

### Multitenancy
A single instance of infrastructure or software serving **multiple independent customers (tenants)** simultaneously, with each logically isolated from the others despite sharing the same physical resources. It is what makes public cloud economically viable — pooled hardware amortized across many customers — and it is the source of the isolation, noisy-neighbor, and data-locality concerns that follow.
