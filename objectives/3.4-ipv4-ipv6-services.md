# 3.4 — Given a scenario, implement IPv4 and IPv6 network services

## Dynamic addressing

### DHCP — the DORA process

| Step | Sent by | Transport |
|---|---|---|
| **D**iscover | Client | **Broadcast** — source `0.0.0.0`, destination `255.255.255.255` |
| **O**ffer | Server | Proposes an address and settings |
| **R**equest | Client | **Broadcast** — accepts one offer |
| **A**cknowledge | Server | Confirms the lease |

**⚠️ Discover is broadcast from `0.0.0.0` because the client has no address yet** and does not know where the server is. This has a direct practical consequence: **a firewall rule matching on source address can never match a DHCP Discover.** Rules permitting DHCP must match on the **incoming interface** instead.

**The Request is broadcast deliberately**, so that servers whose offers were declined learn they may release the addresses they had reserved.

### Scope
**The range of addresses a server may assign on a given subnet**, together with the settings issued alongside them — subnet mask, default gateway, DNS servers, and lease time. Normally one scope exists per subnet or VLAN.

### Exclusions
**Addresses within the scope range that the server must not assign** — most often because a device on that subnet holds one of them statically.

Without the exclusion, the server eventually offers that address to another host and **both devices develop intermittent connectivity**, which is the duplicate-address failure described under IPAM in objective 3.1.

**⚠️ Exclusions solve a problem that address planning prevents.** A scheme placing all static assignments **below** the pool range leaves nothing inside the scope to exclude:

```
.1          gateway
.2 - .99    static assignments   (outside the scope)
.100 - .200 DHCP pool            (the scope)
```

Both approaches function. One requires maintaining a list of holes within the range and remembering it exists; the other makes the collision structurally impossible.

### Lease time
**How long a client may use an address before it must renew.**

| Timer | At | Client action |
|---|---|---|
| **T1** | **50%** of the lease | **Unicasts** a renewal to the original server |
| **T2** | **87.5%** (7/8) | **Broadcasts** a rebind request to **any** server |
| Expiry | 100% | **Must stop using the address** |

**The escalation is deliberate:** ask the known server, then ask anyone, then give up. A client whose server has failed can still be rescued at T2 — provided another server exists.

| | **Short lease** | **Long lease** |
|---|---|---|
| Address recycling | **Fast** | Slow |
| DHCP traffic | More | Less |
| Server dependency | **Higher** | Lower |
| Suits | Guest Wi-Fi, high churn | Stable offices |

Typical values are **1–4 hours** for guest networks and **8 days** for a corporate LAN.

**⚠️ Lease time determines tolerance of a DHCP server outage.** Clients continue working until their leases expire, so an eight-day lease provides days in which to notice and repair a failed server, while a one-hour lease causes network-wide failure within the hour. **This only applies where the DHCP server can fail independently of the network** — a router serving its own subnets offers no such scenario.

**⚠️ Long leases exhaust pools where churn is high.** A venue with a /24 and a 24-hour lease holds addresses for devices that left hours earlier. **The pool must accommodate every device arriving within one lease period**, not merely those present simultaneously.

### Reservations
**The server always assigns a specified MAC address the same IP.**

| | **Static IP** | **DHCP reservation** |
|---|---|---|
| Configured on | The **device** | The **server** |
| Uses DHCP | No | **Yes** |
| Survives a DHCP outage | **Yes** | **No** |
| Changing subnet-wide settings | Visit every device | **One location** |

**Reservations centralise management** — altering a gateway or DNS server updates every reserved device at its next renewal.

**⚠️ A reservation is still a lease.** A reserved device that boots while the DHCP server is unavailable receives nothing, whereas a statically configured device works regardless. That distinction is irrelevant in normal operation and decisive during an outage.

**The decision rule: could this device failing to obtain an address prevent you from repairing DHCP?** If so, configure it statically. Routers, switches, DNS servers, hypervisors, and the management workstation belong on that side; printers, cameras, and application servers do not.

### Options
Configuration delivered alongside the address.

| Option | Delivers |
|---|---|
| **3** | Default gateway |
| **6** | DNS servers |
| 15 | Domain name |
| **42** | NTP servers |
| 51 | Lease time |
| **66 / 67** | TFTP server and boot filename — **PXE boot** |
| **43** | Vendor-specific information |
| 150 | TFTP server (Cisco, VoIP provisioning) |

**Options are how devices bootstrap themselves.** A machine with no operating system uses 66 and 67 to locate its boot image; a VoIP phone uses 150 or 66 to find its provisioning server; and **a lightweight access point commonly uses option 43 to discover its wireless controller** — the discovery step referred to in objective 2.3.

**Options inherit hierarchically** — server-level, then scope-level, then reservation-level, with **the most specific winning.**

**⚠️ A client only receives options it requested.** Every request carries a **Parameter Request List** (option 55). A server may offer an option indefinitely; if the client never asks for it, it is never applied. "The option is configured and nothing happened" is therefore usually a client-side matter rather than a scope misconfiguration.

**Note that addressing and option delivery are separable.** A client with a static address can obtain options alone using **DHCPINFORM**, which returns configuration without allocating an address or creating a lease.

### Relay / IP helper
**DHCP Discover is a broadcast, and broadcasts do not cross routers** — so a client cannot reach a DHCP server on another subnet.

A **relay agent** (Cisco: `ip helper-address`), configured on the router interface facing the clients, **converts the broadcast into a unicast** addressed to a configured server and relays the reply back.

**⚠️ The `giaddr` field is how one server serves many subnets.** The relay writes its own interface address into the packet's **gateway IP address** field, and the server reads it to select the correct scope. Without it the server could not determine which subnet the client is on, since the unicast arrives from the router.

**Option 82** allows the relay to record which physical port or circuit a request arrived on, enabling per-location policy and logging.

**⚠️ `ip helper-address` forwards more than DHCP.** On Cisco it relays eight broadcast UDP services by default — including TFTP, DNS, NetBIOS name and datagram services, and TACACS. Trim the unwanted ones with `no ip forward-protocol udp <port>`.

**Relay is unnecessary where the DHCP server has an interface in each client subnet**, as when a router serves its own VLANs.

### Stateless address autoconfiguration (SLAAC)
How an IPv6 host configures its own address with no server involved.

1. Host generates a **link-local** address (`fe80::/10`) from its interface identifier
2. **DAD** — Duplicate Address Detection: it queries for its own address, and silence confirms uniqueness
3. Sends a **Router Solicitation** to `ff02::2`
4. Router replies with a **Router Advertisement** carrying the **/64 prefix**
5. Host combines the prefix with its interface identifier to form a global address

Routers also transmit Router Advertisements **unsolicited and periodically**.

| Interface identifier | Derivation | Concern |
|---|---|---|
| **EUI-64** | From the MAC — split it, insert `FFFE`, invert the seventh bit | **⚠️ The MAC is embedded**, making the host trackable across networks |
| **Privacy extensions** | Random, rotated periodically | None — **and now the default on most operating systems** |

**"Stateless" means no server records who holds what** — no leases and no bindings, in contrast to **DHCPv6**, which is stateful.

**⚠️ SLAAC alone provides no DNS servers.** Router Advertisements originally carried no such option. Two remedies exist: **RDNSS**, a DNS option carried within the RA, and **stateless DHCPv6**, where the address is self-configured and only options come from DHCPv6 — the same separation of addressing from configuration that DHCPINFORM provides in IPv4.

**The M and O flags in the Router Advertisement select the mode:**

| M | O | Result |
|---|---|---|
| 0 | 0 | **Pure SLAAC** |
| 0 | 1 | **SLAAC plus stateless DHCPv6** |
| 1 | — | **Stateful DHCPv6** |

**⚠️ Any device can send a Router Advertisement, and hosts accept them unauthenticated.** A rogue RA redirects traffic through the attacker exactly as a rogue DHCP server would — and it works on networks where IPv6 was never deliberately enabled, because hosts autoconfigure regardless. **RA Guard** on switch access ports is the defence.

## Name resolution

### DNS resolution
The namespace is hierarchical and **read right to left** — root, then TLD, then the zone. **No server holds the whole tree**; each level knows only where to find the next.

Resolving a name:

1. The client asks its configured **resolver** and waits for a final answer
2. The resolver checks its **cache**
3. Otherwise it asks a **root** server, which refers it to the TLD servers
4. It asks the **TLD** server, which refers it to the zone's nameservers
5. It asks the **authoritative** server, which returns the address
6. The resolver **caches** the result and answers the client

**⚠️ Recursive and iterative queries both occur in a single lookup, at different points:**

| | Query type | Meaning |
|---|---|---|
| Client → resolver | **Recursive** | "Obtain the answer, however many steps are required" |
| Resolver → root, TLD, authoritative | **Iterative** | "Tell me what you know and I will follow the referral" |

**The client asks one question; the resolver asks several.** Centralising that work in resolvers is what makes caching effective.

**Every record carries a TTL** governing how long resolvers may cache it. Long values reduce query load but delay propagation of changes; short values do the reverse. **The practical habit is to lower the TTL in advance of a planned change**, wait for the previous value to expire, and then make it.

**Ports: UDP 53** for ordinary queries, **TCP 53** for zone transfers and responses too large for UDP.

### Record types

| Record | Maps | Note |
|---|---|---|
| **A** | Name → **IPv4** | |
| **AAAA** | Name → **IPv6** | "Quad-A" — 128 bits, four times the 32 of an A record |
| **CNAME** | Name → **another name** | Requires a second lookup |
| **MX** | Domain → **mail server** | Carries a preference value; lower is preferred |
| **TXT** | Name → **arbitrary text** | SPF, DKIM, DMARC, domain verification |
| **NS** | Zone → **authoritative servers** | Used for delegation |
| **PTR** | **IP → name** | Reverse lookups |

**⚠️ CNAME constraints:** it cannot coexist with other records for the same name; it **cannot exist at the zone apex** (which is why providers offer non-standard ALIAS/ANAME records); and **an MX record must not point at a CNAME.**

**⚠️ PTR records reverse the address** — `93.184.216.34` becomes `34.216.184.93.in-addr.arpa`. The reversal exists because **DNS is hierarchical right to left while IP addresses are hierarchical left to right**, so addresses must be inverted to be delegated within the tree. Its principal use is mail: receiving servers check that a sending address resolves back to a matching name, and **a missing or mismatched PTR is a common cause of legitimate mail being rejected.**

**TXT carries the entire email authentication stack** because it was the only record type with no defined structure to violate.

### Zone types, authority, and replication
A **zone** is a portion of the namespace a server has authority over.

| | Direction | Contains |
|---|---|---|
| **Forward zone** | **Name → IP** | A, AAAA, MX, TXT, NS |
| **Reverse zone** | **IP → name**, in `in-addr.arpa` / `ip6.arpa` | PTR |

**⚠️ The two are entirely separate and are not linked automatically** — creating an A record does not create a PTR record. **They are also usually controlled by different parties:** the forward zone belongs to the domain owner, while the reverse zone belongs to whoever owns the IP block, normally the ISP or hosting provider. **Creating a PTR record therefore often requires a request to the provider.**

| | Meaning |
|---|---|
| **Authoritative** | The server **holds the zone data** |
| **Non-authoritative** | The server is **answering from cache** |

Diagnostic tools label this explicitly — the `Non-authoritative answer:` header indicates a cached response.

| | Holds | Changes made |
|---|---|---|
| **Primary** | The **writable original** zone file | Here |
| **Secondary** | A **read-only copy** received by transfer | Never |

Replication uses **zone transfers over TCP 53** — **AXFR** for a full transfer and **IXFR** for incremental. Secondaries compare the **SOA serial number** to decide whether a transfer is needed, and **NOTIFY** allows the primary to signal a change rather than waiting for the refresh timer.

**⚠️ Primary and secondary are both authoritative.** The two distinctions answer different questions: *authoritative or not* asks whether the server holds the zone, while *primary or secondary* asks where its copy originated. **Non-authoritative means cached**, which describes resolvers rather than secondaries.

**⚠️ The classification applies per zone, not per server.** A single instance may be primary for one zone, secondary for another, and non-authoritative for everything else.

**⚠️ Unrestricted zone transfers disclose the entire zone** — every hostname and address in a single query. Transfers must be restricted to known secondaries by address or TSIG key.

### DNSSEC, DoT, and DoH
**DNS was designed without security**, producing two distinct problems with two distinct solutions:

```
DNSSEC   ->  is this answer genuine?     (authentication + integrity)
DoT/DoH  ->  can anyone read this?       (confidentiality)
```

**⚠️ They are not alternatives**, and conflating them is the most common misunderstanding in this area.

**DNSSEC** adds cryptographic signatures to records, allowing a resolver to verify that an answer originated from the authoritative source unmodified. A **chain of trust** runs from the root downward, each level signing the keys of the next.

| Record | Purpose |
|---|---|
| **RRSIG** | Signature over a record set |
| **DNSKEY** | Public key used for verification |
| **DS** | Delegation Signer — links a child zone's key into its parent |
| **NSEC / NSEC3** | Proof that a name does **not** exist |

**⚠️ DNSSEC does not encrypt anything.** Records remain plaintext and remain readable by anyone on the path — they simply cannot be forged. *(NSEC originally permitted **zone walking**, enumerating a zone by following non-existence proofs; **NSEC3** hashes the names to mitigate this.)*

| | **DNS over TLS (DoT)** | **DNS over HTTPS (DoH)** |
|---|---|---|
| Port | **853** — dedicated | **443** — shared with web traffic |
| Encrypted | Yes | Yes |
| **Identifiable on the network** | **Yes** | **No** |
| Blockable | Straightforward | **Very difficult** |

**DoT conceals the content of DNS while remaining visibly DNS. DoH conceals that DNS is occurring at all.**

**⚠️ DoH is a privacy improvement for users and a visibility loss for defenders.** When a browser sends DNS to its own resolver over 443, network-level DNS filtering ceases to apply, DNS logging goes blind, and malware can conceal command-and-control lookups within ordinary HTTPS. Both positions are legitimate, and the conflict is unresolved.

**Mitigations** include the **canary domain** `use-application-dns.net` — browsers disable DoH when it fails to resolve — enterprise policy, and blocking known DoH resolver addresses, the last of which is brittle.

### Hosts file
A local text file mapping names to addresses, **consulted before DNS** — `/etc/hosts` on Linux and macOS, `C:\Windows\System32\drivers\etc\hosts` on Windows.

**Legitimate uses:** testing a change before altering DNS, blocking domains by mapping them to `127.0.0.1`, and resolving names that must work before DNS is available.

**⚠️ Because it takes precedence, a stale entry silently overrides the correct DNS answer.** The characteristic symptom is **one machine resolving a name differently from every other machine**, and the file is rarely the first place anyone looks. It is also entirely unmanaged — an entry exists on one host, appears in no inventory, and survives every subsequent DNS change.

**⚠️ It is a known malware persistence technique.** Redirecting antivirus and update domains to `127.0.0.1` prevents a compromised host from retrieving definitions or patches, cheaply and invisibly. **Checking the hosts file belongs in early troubleshooting** for any "works on one machine but not another" resolution problem.

## Time protocols

### NTP
**Network Time Protocol**, on **UDP 123**, synchronises clocks across a network.

**The stratum hierarchy** describes distance from a reference clock — stratum 0 is the reference itself (atomic clock or GPS), stratum 1 is directly attached to one, stratum 2 synchronises to a stratum 1 server, and so on.

**⚠️ Stratum measures distance, not accuracy.** Devices several strata apart still agree closely, so differing stratum levels are **not** a cause of clock disagreement — misconfiguration, unreachable sources, and time zone errors are.

Accuracy is **milliseconds across the internet and sub-millisecond on a LAN**. NTP queries multiple sources and statistically discards outliers rather than trusting any single one.

**⚠️ Accurate time is a security dependency, not merely an operational convenience:**

| Depends on time | Failure |
|---|---|
| **TLS certificates** | Valid certificates rejected as not yet valid or expired |
| **Kerberos** | **Five-minute skew tolerance** — beyond it, authentication fails |
| **TOTP / MFA** | Codes derived from time become incorrect |
| **Log correlation** | Causal ordering across devices becomes impossible |

**NTP has no authentication by default**, which is what NTS addresses.

### PTP
**Precision Time Protocol (IEEE 1588)** provides **sub-microsecond** accuracy where NTP's milliseconds are insufficient.

| | **NTP** | **PTP** |
|---|---|---|
| Accuracy | Milliseconds | **Sub-microsecond** |
| Timestamping | In software | **In hardware, on the NIC** |
| Network support required | None | **Yes** |

**Hardware timestamping removes scheduling jitter** — the packet is timestamped as it reaches the wire rather than when the operating system next schedules the process.

**⚠️ The remaining error source is variable queuing delay in switches**, which requires the network to participate:

| Device | Role |
|---|---|
| **Grandmaster clock** | The reference source |
| **Boundary clock** | Terminates and regenerates timing per segment |
| **Transparent clock** | **Measures its own queuing delay** and corrects the timestamp in transit |

**Running PTP across switches that do not support it forfeits most of the precision**, since the variable delay it exists to eliminate goes unmeasured.

**Used where milliseconds are inadequate:** financial trading subject to timestamping regulation, telecom base station synchronisation, industrial automation, broadcast video, and scientific instrumentation.

### NTS
**Network Time Security** adds **authentication** to NTP — a TLS-based key exchange followed by cryptographically authenticated NTP packets, preventing an attacker from spoofing time.

**⚠️ It authenticates without encrypting.** Timestamps are not secret; they need to be genuine.

**This is a recurring structural pattern in infrastructure protocols:**

| Protocol | Provides | Does not provide |
|---|---|---|
| **DNSSEC** | Authentication, integrity | Confidentiality |
| **NTS** | Authentication, integrity | Confidentiality |
| **OSPF authentication, RPKI** | Authentication, integrity | Confidentiality |

**DNS answers, time, and routing information are public by nature** — every party receives the same values. What matters is that the values are authentic. **Confidentiality, where wanted at all, is a separate problem solved separately** — which is why DoH exists alongside DNSSEC rather than replacing it.
