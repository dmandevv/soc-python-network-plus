# 2.2 — Given a scenario, configure switching technologies and features

## Virtual Local Area Network (VLAN)

A **logical segmentation of a switch into separate broadcast domains**, independent of physical layout. Ports assigned to different VLANs behave as though they were on entirely separate switches, even in the same chassis.

**What it provides:**
- **Broadcast containment** — each VLAN floods only within itself, so a broadcast storm affects one segment
- **Security segmentation** — devices in different VLANs cannot reach each other without passing a Layer 3 device where policy can be applied
- **Logical grouping independent of location** — a finance VLAN can span three floors while the marketing VLAN shares the same switches
- **Simplified moves and changes** — reassigning a port is a configuration change, not a cabling change

**The key property: a VLAN is a broadcast domain.** Traffic between VLANs is *routed*, not switched — which is why inter-VLAN communication requires a router, a Layer 3 switch with SVIs, or subinterfaces.

**Range:** VLAN IDs are **12 bits**, giving 0–4095. **1–4094 are usable** (0 and 4095 reserved), and 1002–1005 are historically reserved on Cisco equipment. This is the ceiling VXLAN's 24-bit VNI exists to escape.

**VLAN 1 is the default** on most switches — every port belongs to it until configured otherwise. Leaving it in production use is a known weakness, since it is also the default native VLAN and a VLAN-hopping vector.

**Troubleshooting signature:** two devices on the same switch that cannot communicate, with all ports up and configured as access ports, is almost always mismatched VLAN assignment.

**Switching vs. routing:** switching moves **frames within** a network using **flat MAC addresses** — an unknown destination is **flooded**, and the same frame is forwarded out a different port. Routing moves **packets between** networks using **hierarchical IP addresses** — an unknown destination is **dropped**, and the Layer 2 header is rebuilt at every hop. A Layer 3 switch performs both, but the two operations remain distinct.

### VLAN database
The switch's stored record of **which VLANs exist** — their IDs, names, and state — separate from the per-port assignments in the running configuration.

**Where it lives:** historically in `vlan.dat` in flash on Cisco switches, deliberately *outside* `running-config`. That separation causes a classic surprise: **erasing the startup configuration does not delete the VLAN database.** A switch "reset to defaults" can boot with its old VLANs still defined.

**VTP (VLAN Trunking Protocol)** is Cisco's mechanism for propagating the database between switches automatically, so a VLAN created once appears fleet-wide.

**Its notorious risk:** VTP uses a **revision number**, and any switch with a higher revision wins. Introducing an old switch that happens to carry a high revision number can **overwrite the VLAN database of the entire domain**, deleting VLANs everywhere and taking down the network. The standard defence is to set new switches to **VTP transparent mode** before connecting them, or avoid VTP entirely.

### Switch virtual interface (SVI)
A **logical Layer 3 interface representing an entire VLAN** on a Layer 3 switch. It has an IP address and typically serves as the **default gateway** for every host in that VLAN.

**What it enables: inter-VLAN routing inside the switch.** With one SVI per VLAN, traffic between VLANs is routed in hardware without ever leaving the chassis — replacing router-on-a-stick and its single-link bottleneck.

**It is not tied to a physical port.** An SVI represents the VLAN itself, so it stays up as long as at least one active port belongs to that VLAN. Unplugging any single cable does not affect it.

**Its other use is management.** A dedicated management SVI gives the switch an IP address for SSH and SNMP access, reachable only from the management VLAN.

**SVI vs. subinterface — the same job, different device:**

| | **Subinterface** | **SVI** |
|---|---|---|
| Device | Router | **Layer 3 switch** |
| Traffic path | Up a trunk and back down | **Stays inside the switch** |
| Bottleneck | One physical link | None |
| Notation | `Gi0/0.10` | `interface vlan 10` |

**In your homelab**, RouterOS performing inter-VLAN routing on the CRS326 is the SVI model — Layer 3 interfaces defined per VLAN inside the switch, rather than a router on a stick.

## Interface configuration

### Native VLAN
The one VLAN on a trunk whose frames are sent **untagged**. Every other VLAN on that trunk carries an 802.1Q tag; the native VLAN's traffic does not.

**Why it exists:** backward compatibility. A device that does not understand 802.1Q — an old hub, an unmanaged switch, a device during boot — still receives usable traffic on the native VLAN because those frames look like ordinary Ethernet.

**The critical requirement: both ends of a trunk must agree.** A native VLAN mismatch means traffic sent untagged from VLAN 1 on one side is received into VLAN 99 on the other — silently merging two broadcast domains with no error reported. The link stays up and the segments bleed into each other.

**⚠️ Its security significance — double-tagging VLAN hopping:** an attacker on the native VLAN sends a frame with **two** 802.1Q tags. The first switch strips the outer tag (it matches the native VLAN, so it is removed as expected) and forwards the frame, which still carries the inner tag. The next switch reads that inner tag and delivers the frame into a VLAN the attacker was never authorised to reach.

**The hardening that defeats it:**
- **Change the native VLAN away from the default VLAN 1**
- Set it to a **dedicated, unused VLAN** carrying no real traffic
- Never place user devices in the native VLAN
- Where supported, force tagging on all VLANs including the native one

### Voice VLAN
A VLAN dedicated to IP phones, letting **one switch port carry both voice and data on separate VLANs**. The PC's traffic arrives **untagged** into the access VLAN; the phone **tags** its own traffic with the voice VLAN ID.

**Why it exists:** phones are typically daisy-chained — wall → phone → PC — on one cable. But voice needs low latency, low jitter, and QoS priority, while data is bulk and tolerant. Separate VLANs allow different treatment and isolate the phone system from user PCs.

**How the phone learns its VLAN:** the switch advertises it via **CDP** (Cisco) or **LLDP-MED** (open standard), so the handset self-configures with no manual setup.

**Note it is effectively a limited trunk on an access port** — two VLANs on one link, one tagged and one untagged, which is the same split a trunk's native VLAN uses.

### 802.1Q tagging
The IEEE standard for carrying **multiple VLANs over a single link** by inserting a 4-byte tag into the Ethernet frame identifying which VLAN it belongs to. Also called **dot1q**.

**Where the tag goes:** between the **source MAC** and the **EtherType**. Its first two bytes are the **TPID**, always `0x8100`, sitting where the EtherType normally would — so a receiver reading `0x8100` knows a tag follows and the real EtherType comes 4 bytes later.

**The tag's four fields:**

| Field | Size | Purpose |
|---|---|---|
| TPID | 16 bits | Fixed `0x8100`, flags a tagged frame |
| **PCP** | **3 bits** | 802.1p **QoS priority**, 0–7 |
| DEI | 1 bit | Drop-eligible under congestion |
| **VID** | **12 bits** | **The VLAN ID** — the source of the 4,094 limit |

**Consequences:** adding a tag pushes the maximum frame from 1518 to **1522 bytes**, and the **FCS must be recalculated** whenever a switch adds or strips one.

**Access vs. trunk ports:**

| | Access port | Trunk port |
|---|---|---|
| VLANs carried | **One** | **Many** |
| Frames | **Untagged** | **Tagged** (except the native VLAN) |
| Connects to | End devices | Switches, routers, APs, hypervisors |

**The end device never sees a tag.** The switch adds it on ingress from an access port and strips it before delivery out another access port — VLANs are entirely a network-side construct.

**Access port hardening:** because access ports are the physically reachable ones, three controls belong here — **disable DTP** (`switchport nonegotiate`) so a port cannot be negotiated into a trunk (the switch-spoofing half of VLAN hopping), **802.1X** to authenticate devices before granting access, and **port security** to limit which or how many MAC addresses may use the port.

### Link aggregation
Combining multiple physical links between two devices into **one logical link**, providing both increased bandwidth and redundancy. Also called an **EtherChannel**, **port channel**, or **bond**.

**Why it beats leaving redundant links to spanning tree:** STP blocks all but one path, so the spare capacity sits idle until a failure. An aggregated bundle uses **every link simultaneously**, and appears to STP as a single logical link — so there is no loop to block.

**LACP (802.3ad)** is the open-standard control protocol that negotiates the bundle dynamically and detects misconfiguration. **PAgP** is Cisco's proprietary equivalent, and links can also be bundled statically with no protocol at all — though static bundling silently misbehaves if the far end is not configured to match.

**⚠️ The limitation that matters:** a **single traffic flow rides one physical link**. Which link is chosen comes from a hash of MAC addresses, IP addresses, or ports depending on configuration. So four bonded 1 Gbps links do **not** give one transfer 4 Gbps — they give *many concurrent flows* an aggregate of 4 Gbps. A single large file copy still moves at 1 Gbps.

**Requirements:** both ends must agree on the configuration, and member links must generally match in speed, duplex, and VLAN membership.

### Speed and duplex
Two interface settings that must match on both ends of a link. **Speed** is the negotiated rate (10/100/1000/10000 Mbps); **duplex** is whether the link transmits in both directions simultaneously (**full**) or one direction at a time (**half**).

**Autonegotiation** is the default and normally correct: both ends advertise their capabilities and settle on the best common configuration. Gigabit and faster **require** it — hard-coding a gigabit link is not standards-compliant.

**⚠️ Duplex mismatch is the classic fault.** If one end is hard-coded to full duplex and the other autonegotiates, the autonegotiating end **cannot detect duplex** and falls back to **half** — leaving one side full and the other half.

**The symptom:** the link comes up and works, but throughput is terrible. The full-duplex side transmits whenever it wants; the half-duplex side, mid-transmission, registers a **collision**. Interface counters show **late collisions**, CRC errors, and runts.

**Why it is so damaging:** normal collisions are retransmitted by the NIC in microseconds. **Late collisions are not retransmitted at the link layer at all** — recovery falls to TCP, whose timers are measured in hundreds of milliseconds. That gap turns a working link into an unusably slow one.

**The rule:** any late collision means duplex mismatch until proven otherwise. And **hard-code both ends or neither** — mixing manual and automatic is what creates the mismatch.

**CSMA/CD collision handling (half-duplex only):** on detecting a collision the station sends a **32-bit jam signal** so every station discards the corrupted frame, aborts, then waits using **truncated binary exponential backoff** — a random integer from 0 to 2ⁿ−1 slot times after the *n*th collision, capped at n=10, giving up after 16 attempts. **No station yields deliberately**; both pick random waits and whoever draws lower transmits first. The range widens with each collision so the algorithm self-adapts to congestion.

### Spanning tree
A Layer 2 loop-prevention protocol that detects redundant paths between switches and **blocks all but one**, leaving a single active path between any two points.

**Why it is necessary:** switches flood broadcasts and unknown unicasts out every port in the VLAN. With a physical loop, a single broadcast circulates endlessly and multiplies, producing a **broadcast storm** that saturates the segment within seconds. Unlike IP, Ethernet frames have **no TTL** — nothing kills a looping frame on its own.

**How it works:** switches elect a **root bridge** (lowest Bridge ID — priority first, MAC as tiebreak), then each non-root switch determines its **root port** (its own lowest-cost path toward the root). On each segment, whichever switch is closer to the root provides the **designated port**. Everything else is **blocked**.

**Port states — STP vs. RSTP:**

| STP (802.1D) | RSTP (802.1w) |
|---|---|
| Blocking → Listening → Learning → Forwarding | **Discarding** → Learning → Forwarding |
| **30–50 seconds** to converge | **Seconds** |

RSTP merges blocking, listening, and disabled into one **discarding** state, and adds **alternate** and **backup** roles that are precomputed so failover is near-instant rather than recalculated.

**Edge ports (PortFast)** skip the delay entirely on ports connected to end devices, since a single host cannot form a loop. **BPDU Guard** shuts such a port down if a BPDU ever arrives — the signature of a switch appearing where only a workstation was expected.

## Maximum transmission unit (MTU)

The largest **payload** a single frame can carry. On Ethernet the default is **1500 bytes** — payload only, excluding the 18-byte header and FCS, which is why the full frame is 1518 (or 1522 with an 802.1Q tag).

### Jumbo frames
Frames carrying a payload of roughly **9000 bytes** instead of 1500.

**Why bigger helps:** every frame costs the same fixed overhead — headers, interrupt handling, CPU cycles — regardless of how much data it carries. One 9000-byte jumbo frame replaces six standard frames, meaning **one set of headers instead of six** and roughly one-sixth the per-packet processing.

**Where it pays off:** iSCSI, NFS, and SAN traffic, backup jobs, and hypervisor migration links — high-volume bulk transfer between a small number of endpoints. It does **not** help low-rate traffic like video streaming, which never approaches the link limit.

**⚠️ Jumbo frames must be enabled on every device in the path.** Every switch, NIC, and router hop. A device left at 1500 does not negotiate down — it **drops the oversized frame silently**. The signature is that ping works and small transfers work while large transfers hang, because a ping is too small to expose the mismatch.

For that reason jumbo frames belong on **isolated, fully controlled segments** — a storage VLAN or dedicated backup network — never on a general-purpose LAN.

### Path MTU Discovery (PMTUD)
How a sender learns the smallest MTU along an entire path without trial and error.

1. The sender sets the **DF (Don't Fragment)** bit on its packets
2. A router whose next link is too small **cannot fragment**, so it drops the packet
3. It returns **ICMP Type 3, Code 4** — "Fragmentation Needed and DF Set" — which **includes the next-hop MTU**
4. The sender shrinks to that size and retries

The reply carries the number, so the sender does not guess.

### ⚠️ MTU black hole
Blocking all ICMP at a firewall kills step 3. The sender never learns the path MTU, keeps sending oversized packets with DF set, and they are **silently discarded indefinitely**.

**Symptoms:** ping works, the TCP handshake completes, then SSH hangs at the banner and web pages return headers before stalling. Small packets pass, large packets vanish — **connectivity tests all succeed while the connection is unusable.**

This is the standard argument against blanket ICMP filtering: **Type 3 Code 4 is load-bearing.**

### Why VPNs break most often

**The cause is encapsulation overhead.** A tunnel wraps the original packet in new headers, so a packet that exactly filled the MTU on the LAN no longer fits on the WAN.

| Encapsulation | Added overhead |
|---|---|
| GRE | ~24 bytes |
| VXLAN | ~50 bytes |
| IPsec ESP (tunnel mode) | ~50–60 bytes |

**The failure, step by step:**

1. Host A and Host B complete a TCP handshake. SYN, SYN-ACK, and ACK are ~40–60 bytes, so they cross the tunnel easily and **the connection establishes normally**
2. Both hosts are on 1500-MTU Ethernet, so they negotiate **MSS 1460** (1500 − 20 IP − 20 TCP)
3. Host A sends its first full data segment: a **1500-byte packet with DF set**
4. The VPN gateway encrypts and encapsulates it, producing ~**1557 bytes**
5. The WAN link is 1500. The packet does not fit, and DF forbids fragmenting it

**If ICMP flows,** the gateway returns Type 3 Code 4 with next-hop MTU ~1443, Host A caches it per-destination and resends smaller. This works.

**If ICMP is blocked,** the packet is dropped with no notification. Host A retransmits **the same oversized packet**, backs off, and eventually times out.

**This is why the symptom is "connects, then hangs."** The handshake is small enough to succeed; the first full-size segment dies. SSH stalls at key exchange because that is the first large exchange, and HTTP returns headers before stalling because the request is small but the response is not.

**Where the ICMP gets lost:** an endpoint firewall dropping inbound ICMP, an intermediate provider filtering it, uRPF discarding it as spoofed, or NAT failing to match it back to the internal host — the ICMP payload embeds the original packet, and NAT must inspect it to know where to return the message.

**The failure can be asymmetric.** Filtering differs by direction, so the connection may work one way and hang the other.

### MSS clamping
The standard fix. A router rewrites the **MSS (Maximum Segment Size)** option inside the TCP SYN as it crosses the tunnel, so both endpoints agree on a smaller segment **before any data is sent**.

**Its advantage: it never relies on ICMP**, so it works even inside a black hole. That is why it is standard tunnel configuration rather than a workaround.

**Its limitation: it only helps TCP.** UDP has no MSS option, so UDP-based traffic must handle path MTU itself — QUIC does this with its own probing rather than depending on ICMP.

**IPv6 makes this stricter:** routers **never** fragment, so PMTUD is mandatory rather than an optimisation, and blocking **ICMPv6 Type 2 (Packet Too Big)** breaks IPv6 harder than blocking ICMP breaks IPv4.

## VLAN hopping — the two attacks side by side

Both are called VLAN hopping, but they use different mechanisms and different countermeasures. Confusing them is a common exam trap.

| | **Switch spoofing** | **Double tagging** |
|---|---|---|
| Method | Attacker sends DTP frames posing as a switch | Attacker sends a frame carrying two 802.1Q tags |
| Result | Port negotiates into a **trunk**; attacker receives every VLAN | Outer tag is stripped, inner tag delivers the frame into another VLAN |
| Requires | A port left in dynamic negotiation mode | Attacker positioned **in the native VLAN** |
| Fix | **Disable DTP** — `switchport mode access` + `switchport nonegotiate` | Move the native VLAN to a dedicated unused ID; keep users out of it |
| Direction | Bidirectional — full access to the VLAN | **One-way only** — no return path exists |

**The keyword that separates them: "negotiate" means DTP means switch spoofing.** Native VLAN hardening does nothing against it, and disabling DTP does nothing against double tagging — they are independent controls and both are needed.
